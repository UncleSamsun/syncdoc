# SyncDoc — 새 MVP 요구 정리

작성일: 2026-09-09
상태: 사용자 요구 수집 / 설계 미확정

## 출발점

SDD 방식으로 에이전트와 개발한다. 기존 구상은 거의 폐기하며, 과거 폴더의 요구·설계·ID·디자인을 자동 승계하지 않는다. 아래 내용은 2026-09-09 사용자의 새 요청을 기준으로 한다.

## 사용자 확인 요구

### 프로젝트 공통 Spec 템플릿

프로젝트 관리가 목적이다. Spec의 종류와 내용을 템플릿화하고 모든 프로젝트에서 같은 템플릿을 기반으로 작업한다. 구체적인 Spec 종류와 필수 필드는 아직 확정하지 않았다. 현재 PRD/UI/Tech/Tasks 폴더는 논의의 출발점이다. [공통 Spec 구성안](spec-standard-proposal.md)에 유형별 필수 내용과 축약 예시를 제안했다.

공통 양식 사용 방식에 대한 후속 사용자 제안: 빈 템플릿을 직접 복사하지 않고 AGENTS.md에 메인 안내를 두며 문서 구조·GitHub 협업 등 상세 규칙은 별도 Markdown으로 작성해 에이전트가 참조하도록 한다. 구체적인 파일 배치와 배포 방식은 미확정이다. 상세는 [공통 Spec 구성안](spec-standard-proposal.md)의 규칙 중심 작성 방식을 참조한다.

### 사람이 읽기 쉬운 문서

2026-09-09 추가 요구: 문서의 표와 다이어그램도 지원하기를 원한다. Java 기반 Markdown 렌더러 대안을 검토하는 맥락에서 나온 요구이며 VitePress 선택 철회나 특정 다이어그램 라이브러리 채택을 뜻하지 않는다. 일반 표와 주요 설계 다이어그램을 우선 검토하고 복잡한 표의 셀 병합·특수 도형 등 세부 범위는 구분한다.

Markdown을 HTML로 보여주는 도구를 검토한다. 형식이 마음에 드는지 실제 화면으로 확인해야 한다. Markdown 또는 HTML이라는 형식 자체보다 사람이 내용을 읽기 쉬운 것이 우선이다. 렌더링 도구와 디자인은 미정이다.

### ID·메타데이터와 SSOT

중복 서술을 줄이고, 한 내용은 한 곳에서 관리하며 다른 곳에서는 ID와 링크로 접근한다. 요구 하나를 바꾸려고 모든 문서를 수정해야 하는 상황을 피한다. 구체적인 ID 문법과 메타데이터 필드는 미정이다.

### Git 저장소 기반 대시보드

관리할 Git 저장소를 연결하고 변경을 신속하게 가져온다. 프로젝트의 현재 상태·진행도·누가 무엇을 작업하는지를 대시보드에서 관리하는 것을 우선 MVP로 한다. 첫 연동 대상은 GitHub로 사용자가 확인했다. 대상 브랜치, 갱신 지연 목표, 상태 및 담당자 정보의 원천은 미정이다.

### 명세에서 GitHub 협업으로 연결

사용자는 기존 작업 관리 방식이 없었다고 확인했다. 먼저 명세에 작업을 정의하고 이를 바탕으로 GitHub Issues·Projects를 이용해 관리한다. 프로젝트 공통 GitHub 협업 프로세스도 함께 정의한다. 세부 운영 규칙은 [협업 프로세스 초안](../04-tasks/collaboration-workflow.md)에서 제안한다.

## 설계 제안 — 사용자 확정과 구분

### 개인·팀 사용과 호스팅 방향

사용자는 개인과 팀 양쪽에서 사용할 것이라고 확인했다. 서비스는 클라우드 또는 사내 서버에 올려 호스팅할 가능성이 높다고 밝혔다. MVP 이용자는 본인과 초대한 팀원으로 확정했으며 공개 가입은 포함하지 않는다. 구체적인 호스트·로그인·초대·저장소 권한 연동은 미정이다. 로컬 전용 도구를 기본 운영 모델로 삼지 않는다. 아래는 이 방향에 따른 설계 제안이며 모두 확정 요구는 아니다.

- 개인도 팀도 같은 웹 서비스를 사용한다. 프로젝트마다 저장소와 접근 가능한 사용자를 연결한다.
- 호스팅 환경에서 사용자 식별과 프로젝트별 접근 제어를 제공한다. 저장소를 연결한 서비스가 데이터를 읽을 수 있다는 사실만으로 모든 로그인 사용자에게 내용을 공개하지 않는다.
- 서버가 문서와 GitHub 협업 정보를 수집한다. 사용자의 브라우저가 닫혀 있어도 갱신할 수 있는 운영 방식을 검토한다.
- 공개 소스 저장소와 서비스 가입 범위는 별개다. 서비스는 초대한 사용자에게 제공하며 공개 가입·결제·복잡한 조직 관리는 MVP 요구에 포함하지 않는다.
- 사내 네트워크의 GitHub 접근과 외부 이벤트 수신 가능 여부를 확인한 후 이벤트 수신/주기적 조회 방식을 선택한다.

### 공통 동작 제안

후속 사용자 제안: GitHub OAuth로 로그인하고 GitHub에서 볼 수 있는 범위만 보여준다. 초대된 사용자만 서비스에 들어오는 기존 제한은 유지한다. [접근 설계 초안](../03-tech-spec/access-proposal.md)에 로그인·초대·관리 대상·GitHub 권한의 교집합과 Project 별도 권한, OAuth App/GitHub App 선택 사항을 정리했다.

- 요구·설계·작업 정의는 프로젝트 저장소의 Markdown에 두고, 실행 담당자·진행 상태는 GitHub Issues·Projects에서 관리하는 방안을 제안한다. 대시보드는 두 원천을 연결한 파생 조회이며, 명세에 실행 상태를 수동으로 중복 기록하지 않는다.
- 공통 템플릿에는 버전을 두고 프로젝트가 사용하는 버전을 기록한다. 템플릿 변경으로 모든 프로젝트 문서를 자동 덮어쓰지 않는다.
- ID는 문서 이동과 제목 변경에도 유지한다. 문서 ID, 항목 참조, 작업의 담당자와 상태에 필요한 최소 메타데이터부터 정한다. 기존 ID 체계는 재사용하지 않는다.
- 동일 요구의 본문은 한 곳에만 작성한다. 다른 문서에서는 링크 또는 원문 미리보기로 제공한다. 원문 변경이 API·DB 등 파생 설계까지 자동으로 올바르게 수정한다는 뜻은 아니다.
- Spec 작성 상태, 작업 완료 상태, Git 활동은 구분한다. 완료율은 상태가 명시된 작업을 기준으로 산출하고 분모와 집계 기준을 표시한다. 커밋 수를 완료율로 바꾸지 않는다.
- 담당자 표시에는 명시적인 작업 배정 정보가 필요하다. 최근 커밋 작성자를 현재 담당자로 단정하지 않는다. 로컬에서 push하지 않은 작업은 저장소 연결만으로 관측할 수 없다.
- Git 변경은 서비스 전용 복제본에 fetch하고 특정 revision을 읽는 방식을 검토한다. 사용자 작업 폴더에서 자동 pull/merge하지 않는다.
- 변경 이벤트 수신과 주기적 재확인을 조합하는 방안을 검토한다. 실패 시 마지막 정상 상태와 마지막 동기화 시각·오류를 표시한다. 새 revision을 읽는 중에는 서로 다른 revision의 문서를 섞어 게시하지 않는다.
- 첫 버전은 저장소에서 작성한 내용을 읽고 집계하는 흐름에 집중하는 방안을 권고한다. 웹 편집기·에이전트 실행 제어·복잡한 승인 엔진은 현재 사용자 확정 요구가 아니다.

## 문서 표시 방식 — 최신 확정

2026-09-09 Java 대안과 표·다이어그램 지원 논의 후 사용자가 추천 조합을 수용했다. Spring Boot 4/Java25에서 commonmark-java와 GFM 표 확장으로 본문·표를 변환하고, React가 문서 화면을 표시하며 Mermaid가 브라우저에서 다이어그램을 렌더링한다. 이전 VitePress 선택은 이 결정으로 대체한다.

프로젝트 선택 → 현황과 문서 목록 → 문서 선택 → 렌더링된 문서라는 흐름을 유지한다. 추가 목업은 필요하지 않다. 일반 표와 흐름도·시퀀스·ERD·클래스·상태도를 우선 지원한다. VitePress에서 보았던 테마·검색·목차는 자동으로 따라오지 않으며 필요한 읽기 기능을 React에서 구성한다.

문서별 Node.js 빌드는 사용하지 않는다. React 앱 자체의 빌드 환경은 별개다. 웹에서 문서를 편집해 MD로 저장하는 기능은 MVP 범위에 추가하지 않았다. 구체적인 렌더링·정화·오류 처리는 기술 설계에서 정의한다.

## 최소 검증 시나리오 제안

1. 두 프로젝트에서 같은 버전의 템플릿으로 문서를 작성한다.
2. 요구 한 곳을 수정하면 두 참조 화면에서 같은 revision의 원문으로 접근한다.
3. 파일 이동 후에도 ID 링크가 유지되고 누락·중복 ID는 명확하게 표시된다.
4. GitHub에서 작업의 담당자·상태를 수정하면 코드 push 없이도 대시보드가 갱신된다.
5. 동기화에 실패하면 이전 정상 상태를 유지하고 오래된 정보임을 표시한다.
6. 같은 호스팅 서비스에서 개인 프로젝트와 팀 프로젝트를 조회하되, 권한이 없는 사용자는 해당 프로젝트의 문서·검색 결과·집계를 조회할 수 없다.
7. 초대되지 않은 사용자는 서비스에 가입하거나 프로젝트 정보를 조회할 수 없다. 로그인 수단을 통과하는 것만으로 가입과 저장소 접근을 허용하지 않는다.

## 다음 확인

첫 연동은 GitHub로 확정했고 명세에서 작업을 정의한 후 Issues·Projects로 협업하는 방향도 확인했다. 개인·팀 모두 사용하며 클라우드 또는 사내 서버에 호스팅한다. 이용자는 본인과 초대한 팀원으로 제한한다. 다음은 로그인·초대·저장소 접근, 문서 읽기 화면을 구체화한다. PR·커밋은 구현 활동의 근거로 연결할 수 있지만 그 자체를 전체 작업 상태로 간주하지 않는다.
