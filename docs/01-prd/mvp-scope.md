# MVP 기능과 인수 기준

이 문서는 첫 구현 기준이다. 아직 구현하지 않았다.

목표·포함 범위·제외 범위·제약·용어는 [프로젝트 개요](overview.md)가 정본이다. 아래 요구는 그 범위 안에서 정의한다. 요구 수집 경과는 [요구 정리](brief.md), 구현 기술은 [아키텍처](../03-tech-spec/architecture-proposal.md)를 따른다. 아래 ID는 이 설계 묶음의 안정적인 참조용이며 전체 ID 발급 규칙을 확정한 것은 아니다. 수치와 운영 기본값은 검토 제안이다.

## REQ-001 초대와 로그인

GitHub OAuth로 신원을 확인하고 서비스 이용을 허용받은 사용자만 세션을 발급한다. GitHub App 사용자 인증을 구현 후보로 한다. 최초 관리자는 배포 설정의 GitHub 사용자 ID로 지정하고, 관리자는 GitHub 계정을 허용 목록에 등록하는 방식으로 초대한다. 이메일 발송과 공개 가입은 제외한다.

**예외:** GitHub 인증이 실패하거나 `state`가 불일치·만료하면 세션을 발급하지 않고 로그인 화면으로 돌린다. 허용 목록을 확인할 수 없으면 진입시키지 않는다. 허용 목록에 없는 계정은 로그인 자체는 성공해도 프로젝트의 존재 여부를 알 수 없다.

**인수 기준:** 미초대 계정은 로그인 후에도 서비스 진입 불가, 초대 취소 시 기존 세션 무효화, 계정명 변경에도 GitHub 사용자 ID로 동일 사용자 식별. 세션·토큰은 브라우저 저장소에 노출하지 않는다.

**근거:** [프로젝트 개요](overview.md)의 대상 사용자다. 이용자를 본인과 초대한 팀원으로 제한했고 공개 가입을 제외 범위에 두었으므로, 신원 확인과 허용 목록이 함께 필요하다.

## REQ-002 프로젝트 연결

MVP 관리 단위는 GitHub 저장소 하나다. 읽기 가능한 후보에서 저장소를 고르고 문서 기준 브랜치와 경로를 설정한다. 기본값은 main과 docs이며 해당 브랜치/경로가 없으면 사용자가 실제 값을 선택한다. 연결 후에는 공통 셸에서 기준 브랜치를 바꿀 수 있다. (2026-09-09 UI 검토에서 기본값을 dev에서 main으로 변경했다. 이는 문서를 읽을 대상 브랜치이며 SyncDoc 자체 개발 브랜치 전략과 무관하다.) 하나의 저장소를 중복 연결하지 않는다. 연결 관리 권한은 등록자 또는 서비스 관리자에게 둔다. 이는 문서 열람 권한을 추가하는 역할이 아니다.

**예외:** 기본값 `main`·`docs`가 저장소에 없으면 사용자가 실제 값을 고른다. 앱만 또는 사용자만 접근할 수 있는 저장소는 후보에 넣지 않는다. 이미 연결된 저장소를 다시 연결하면 프로젝트를 늘리지 않고 이미 열람할 수 있는 프로젝트를 알린다. GitHub Project를 연결하지 않으면 문서와 Issue·PR 현황만 제공한다.

**인수 기준:** 앱과 사용자 모두 접근 가능한 저장소만 연결, 중복 요청은 같은 프로젝트를 반환하거나 409로 안내, 임의 URL/로컬 경로 연결 불가, 등록 직후 첫 수집 대기 상태 표시. GitHub Project는 선택 연결하며 없으면 문서와 Issue/PR 현황만 제공한다.

**근거:** [프로젝트 개요](overview.md)의 목표다. 저장소를 연결하는 것이 명세와 실행 상태를 잇는 출발점이고, 용어 정의상 저장소 하나가 프로젝트 하나다.

## REQ-003 현황과 작업

프로젝트 선택 시 최근 변경·동기화 시각·담당 작업·상태별 건수·문서 목록을 보여준다. 작업 정의의 정본은 MD, 실행 담당자·상태의 정본은 GitHub다. 상태·완료 규칙은 [협업 규칙](../../rules/github-collaboration.md)을 참조한다.

**예외:** Project 권한이 없으면 Project 상태와 완료율을 조회 불가로 두고 추정하지 않는다. 분모가 0이면 계산 대상 없음으로 표시한다. 페이지 수집이 끝나지 않았으면 완료율을 확정하지 않는다. 배포 연동 전에는 배포 상태를 미수집으로 표시한다. 수집이 실패한 동안에는 마지막 정상 값과 그 기준 시각을 함께 보여준다.

**인수 기준:** 작업과 PR을 중복 집계하지 않음, 취소를 완료에서 제외, 명세의 확정 작업 중 Issue 미등록도 미등록으로 표시. Project 권한이 없으면 Project 상태와 완료율은 null/조회 불가로 표시하며 추정하지 않음. 분모 0은 계산 대상 없음. 전체 데이터의 페이지 수집이 끝나지 않으면 완료율을 확정하지 않음. dev 개발 완료와 main 릴리스/실제 배포는 구분하며 배포 연동 전에는 배포 상태 미수집으로 표시.

**근거:** [프로젝트 개요](overview.md)의 문제다. 명세의 작업 정의와 GitHub의 실행 상태를 사람이 머릿속에서 맞추고 있다는 것이 이 요구의 출발점이다.

## REQ-004 문서 읽기

목록에서 문서를 선택하면 Java가 변환한 본문과 일반 표를 React 화면에서 보여준다. 목차·일반 Markdown 링크·명시적 앵커·허용된 접기·코드·이미지를 지원한다. 검색은 현재 프로젝트의 문서 제목·본문을 대상으로 한다. 웹 편집은 제외한다.

**예외:** 셀 병합과 다단 표는 범위 밖이며 원문 그대로 보여준다. 첫 수집이 끝나기 전에는 문서 목록이 비어 있고 본문 조회는 아직 준비되지 않았음을 알린다. 권한이 없는 이미지와 권한이 없는 문서는 없는 것과 같은 응답으로 답해 존재 여부를 추론할 수 없게 한다.

**인수 기준:** 링크 목적지/앵커 이동, 같은 게시 revision의 문서 간 탐색, 이미지 권한 확인, 검색 결과와 목록에도 권한 적용. 파일 이동은 MD 링크를 함께 고치는 확정 규칙을 따른다. 셀 병합과 다단 표는 범위 밖이다.

**근거:** [프로젝트 개요](overview.md)의 목표다. 명세를 저장소에 두고 한 화면에서 읽는다는 것이 이 제품의 본체이며, 웹 편집은 제외 범위다.

## REQ-005 다이어그램

Mermaid 코드 블록의 흐름도·시퀀스·ERD·클래스·상태도를 브라우저에서 표시한다. 원문은 HTML과 분리된 텍스트로 전달한다.

**예외:** 문법 오류·과대 입력·시간 초과는 해당 블록에만 오류로 표시하고 나머지 문서는 그대로 읽힌다. 제한을 넘으면 그리지 않고 원문 보기로 대체한다. 다이어그램 하나가 문서 전체를 못 읽게 만들지 않는다.

**인수 기준:** 다섯 유형의 샘플 모두 표시, 코드 오류·과도한 입력은 해당 블록에만 오류 표시, 나머지 문서는 읽기 가능. 외부 실행/임의 설정 변경을 허용하지 않음. 비교 기준으로 블록당 20KB, 문서당 20개, 렌더링 3초 제한을 제안하며 초과 시 원문 보기로 대체한다.

**근거:** REQ-004의 읽기 대상에 다이어그램이 포함된다. 이 프로젝트의 명세 자체가 Mermaid 블록을 쓰므로, 그림이 코드로 보이면 문서를 읽는 목적이 달성되지 않는다.

## REQ-006 GitHub 변경 반영

이벤트 또는 주기 조회로 갱신하고 문서가 달라진 경우만 다시 변환한다. 최초 조회 간격은 60초, 화면 상태 확인은 화면을 보는 동안 20초를 제안한다. 이 수치는 갱신 완료 SLA가 아니다.

**예외:** 수집이 실패하면 마지막 정상 snapshot을 유지하고 실패 시각과 다음 재시도 시각을 함께 보여준다. 실패한 수집이 기존 정상 데이터를 덮어쓰지 않는다. 중복 이벤트는 같은 작업을 두 번 예약하지 않는다. 부분 수집을 빈 목록이나 완료로 오인하지 않는다. 최초 수집이 실패하면 빈 문서 목록과 수집 오류를 함께 보여준다.

**인수 기준:** 중복 이벤트/동시 실행에도 일관된 게시본, 수집 실패 시 마지막 정상 데이터와 실패 시각을 구분, 재시작 후 작업 재개, 부분 수집을 빈 목록/완료로 오인하지 않음. 렌더러나 정화 정책 버전이 바뀌면 원문이 같아도 다시 변환한다.

**근거:** [프로젝트 개요](overview.md)의 목표다. 어느 쪽도 다른 쪽에 수동으로 복사하지 않는다고 했으므로, 저장소가 바뀌면 서비스가 스스로 따라가야 한다.

## REQ-007 접근 범위

초대·로그인·관리 대상 연결·요청자의 GitHub 권한 교집합만 허용한다. GitHub Project 권한은 저장소와 따로 확인한다. 원칙은 [접근 설계](../03-tech-spec/access-proposal.md)를 따른다.

**예외:** GitHub 권한을 확인할 수 없으면 503 또는 429로 제한하고, 예전에 허용됐다는 사실을 근거로 내용을 반환하지 않는다. 확인 불가는 허용도 거절도 아닌 별개 상태로 다룬다. 권한 없는 대상과 없는 대상은 같은 응답으로 답한다.

**인수 기준:** 다른 계정으로 수집한 캐시를 권한 없는 사용자에게 반환하지 않음. 문서·원문·다이어그램·첨부·검색·집계 모두 적용. 최초 MVP에서는 보호된 요청마다 사용자 자격증명으로 GitHub 권한을 확인하고 요청 안에서만 결과를 재사용한다. 확인 불가 시 503/429로 제한하며 예전 허용을 근거로 내용을 반환하지 않음. 나중에 권한 캐시를 추가할 경우 철회 반영 지연을 별도로 합의한다.

**근거:** [프로젝트 개요](overview.md)의 목표에 있는 "자신의 권한 범위 안에서 읽는다"가 이 요구다. 여러 사용자가 같은 프로젝트를 보는데 GitHub의 권한 경계를 서비스가 무너뜨리면 저장소를 연결할 수 없다.

## REQ-008 공통 작성 규칙

AGENTS.md는 진입점, 상세 MD는 문서 작성·ID·SDD·GitHub·검증 규칙이다. 프로젝트는 적용 규칙 버전을 기록한다. 이번 MVP 개발은 이 프로젝트에 규칙을 완성하고 두 번째 샘플 프로젝트에도 같은 기준을 적용해 검증한다. 조직 전체 자동 업데이트 시스템은 제외한다.

### 기준의 정본 위치 (2026-09-10 사용자 확정)

프로젝트를 진행하는 기준, 나와야 하는 산출물 목록, 산출물마다 필수로 작성할 내용은 모두 **대상 저장소의 규칙 파일**에 둔다. Git이 버전·이력·리뷰를 담당한다. SyncDoc은 이 기준을 읽어 준수 여부를 조회·표시하고, 기준 자체를 서비스에서 저작·편집하지 않는다. 서비스가 기준의 정본이 되는 방식은 "명세가 정본, GitHub이 상태"라는 이 제품의 전제와 어긋나므로 채택하지 않는다.

이에 따라 산출물 목록과 산출물별 필수 내용은 [공통 Spec 구성안](spec-standard-proposal.md)의 검토 표에서 활성 규칙 파일로 승격시킨다. 승격 전까지 그 표는 제안이며 활성 규칙이 아니다.

SyncDoc이 제공할 표시 범위는 **산출물 체크리스트**다. 적용 유형에서 있어야 할 문서, 없는 문서, 필수 내용이 빠진 문서와 그 항목을 프로젝트 단위로 보여준다. 기준을 고치는 화면은 만들지 않는다.

**예외:** 규칙 파일이 없는 프로젝트는 미검사로 표시하고 통과로 표시하지 않는다. 검사기가 확인하지 않는 항목을 검증 통과로 표시하지 않는다. 적용하지 않는 문서 종류는 사유를 함께 적어야 하며, 사유 없이 빠뜨린 것과 구분한다.

**인수 기준:** 요구·설계·작업의 필수 항목, 중복 ID, 깨진 링크를 검사하고 오류 위치를 제시. 문서와 작업 상태는 중복 관리하지 않음. 파서/검증기가 구현되기 전에는 검증 통과라고 표시하지 않음. 적용 규칙 버전은 프로젝트 설정 한 곳에서 읽으며 문서마다 수동 복사하지 않음. 산출물 체크리스트는 활성 규칙 파일을 근거로 하며, 규칙 파일이 없는 프로젝트는 미검사로 표시하고 통과로 표시하지 않음.

**근거:** 2026-09-10 사용자 확정이다. 프로젝트 관리 플랫폼을 만들면서 그 프로젝트가 지켜야 할 기준과 필수 산출물 목록이 어디서 관리되는지가 어느 문서에도 없다는 것을 사용자가 지적했고, 그 답을 이 요구로 정했다.

## 검토할 기본값

저장소 1개=프로젝트 1개, main/docs 기본값, GitHub ID 허용 목록 초대, GitHub App 인증, Project 선택 연결을 제안한다. 실제 앱 설치·자격증명·조직 권한은 구현 전 연결 실험이 필요하다. 이 문서는 계획 검토용이며 해당 조건이 이미 운영된다는 뜻이 아니다.
