# 공통 Spec 템플릿 구성안

## 목적

모든 프로젝트가 같은 기준으로 요구·설계·작업을 작성하고 사람이 읽으며 GitHub 협업으로 이어갈 수 있게 한다. 기존 구상을 승계하지 않고 새 요구를 기준으로 작성했다. 이 문서는 공통 템플릿의 구성 제안이며 관리 대상 프로젝트의 실제 명세가 아니다.

추천은 4개 영역을 유지하고 유형별 필수 내용을 정의하는 방식이다. 파일 개수를 고정하지 않는다. 모든 문서를 무조건 생성하지도 않는다. 프로젝트 특성에 따라 적용 유형을 먼저 정하고, 적용하지 않는 유형은 사유를 남긴다.

## 1. 구성 대안

| 방식 | 장점 | 한계 |
|---|---|---|
| 영역별 한 파일, 총 4개 | 시작이 간단함 | 화면·API·작업이 늘면 파일과 변경 범위가 커짐 |
| 4개 영역 + 유형별 템플릿, 기능별 분리 — 추천 | 같은 필수 기준을 유지하면서 규모에 맞게 분리 | 적용 유형과 참조 규칙이 필요함 |
| 프로젝트마다 자유 양식 | 초기 제약이 적음 | 공통 작성·검증·집계 기준을 유지하기 어려움 |

## 2. 영역과 필수 내용 — 승격 완료

이 절의 문서 종류·적용 조건·필수 내용 표는 2026-09-10에 [문서 작성 규칙](../../rules/spec-writing.md) §3으로 승격되었다. 활성 규칙은 그 파일이며 여기에 중복 본문을 두지 않는다.

SyncDoc은 호스팅 웹 서비스이므로 UI·인터페이스·데이터·운영 유형을 모두 검토할 필요가 있다. 이는 DB나 인증 기술을 확정한다는 뜻이 아니다.

## 3. 문서의 공통 정보 — 승격 완료

이 절의 메타데이터 항목과 문서 구성 지침은 2026-09-10에 [문서 작성 규칙](../../rules/spec-writing.md) §2·§4로 승격되었다. 실제 채택한 메타데이터는 `id`·`type`·`status` 세 필드이며, 템플릿 버전과 규칙 버전은 [프로젝트 설정](../../rules/project-settings.md) 한 곳에서 관리한다. 여기에 중복 본문을 두지 않는다.

## 4. ID와 중복 방지 원칙 — 승격 완료

이 절의 ID 부여·유일성·중복 방지 원칙은 2026-09-10에 [문서 작성 규칙](../../rules/spec-writing.md) §6·§7로 승격되었다. 참조 문법은 [ID와 문서 참조](../../rules/identity-and-references.md)가 정본이다. 여기에 중복 본문을 두지 않는다.

## 5. 축약 작성 예시

아래는 템플릿을 이해하기 위한 가상 예시다. ID 표기와 기능 범위를 확정한 것이 아니며 실제 Issue도 아니다.

이 예시의 라벨 이름과 배치는 승격 전 형태다. **실제 문서를 쓸 때 여기를 베끼지 않는다.** 확정된 라벨 이름 공간과 표기 방식은 [문서 작성 규칙](../../rules/spec-writing.md) §5이며, 라벨 뒤 내용은 같은 줄에서 시작해야 한다.

### 요구 항목

**요구 ID:** REQ-001 (예시)

**제목:** 연결한 저장소의 동기화 상태 확인

**사용자 필요:** 사용자는 대시보드 정보가 최신인지 판단하고 싶다.

**기대 동작:** 저장소마다 마지막 정상 반영 시각과 최근 동기화 결과를 확인할 수 있다.

**인수 기준:**
- 첫 동기화 전에는 미동기화 상태임을 표시한다.
- 동기화가 성공하면 정상 반영 시각을 갱신한다.
- 이후 동기화에 실패하면 마지막 정상 데이터를 유지하고 실패를 표시한다. 실패한 상태를 최신 데이터인 것처럼 표시하지 않는다.

**근거:** 새 MVP의 GitHub 대시보드 요구를 구체화한 검토 예시.

### 화면 항목

**화면 ID:** UI-001 (예시)

**제목:** 프로젝트 현황

**연결 요구:** REQ-001의 원문 링크

**화면 설계:** 카드에 동기화 상태와 시각을 배치한다. 오류는 색상과 텍스트로 표시한다. 상세 화면에서 마지막 오류 내용을 확인한다.

**상태별 표현:** 미동기화/동기화 중/성공/실패의 배치와 문구를 작성한다. 성공·실패의 의미는 요구 원문을 참조한다.

### 작업 정의

**작업 ID:** TASK-001 (예시)

**제목:** 프로젝트 카드에 동기화 상태 표시

**연결:** REQ-001, UI-001, 관련 인터페이스 계약

**범위:** 명시된 동기화 결과를 화면에 표시한다. 동기화 수집 엔진 자체는 별도 작업으로 다룬다.

**선행 조건:** 동기화 상태 계약 확정.

**검증:** 첫 동기화 전, 성공 후, 성공 뒤 실패한 경우를 화면에서 확인하고 REQ-001 인수 기준 충족을 검증한다.

**산출물:** 화면 변경과 검증 증거를 담은 PR.

담당자와 현재 실행 단계는 Issue·Project에서 읽는다. 작업 정의의 완료 조건은 판단 기준이며 현재 완료 여부가 아니다.

## 6. 작성 순서와 GitHub 연결

프로젝트 개요와 적용 유형을 정하고 기능 단위로 요구를 구체화한다. 그 기능에 필요한 UI·기술 설계를 작성한 뒤 구현 가능한 작업을 Issue로 등록한다. 전체 프로젝트의 모든 설계를 완성해야 첫 작업을 시작할 수 있다는 전제를 두지 않는다.

관련 미확정 조건·의존성·인수 기준을 해결한 후 작업을 시작한다. Issue에는 요약·명세 링크·시작 기준 revision을 남긴다. 실행 상태와 담당자는 GitHub에서 갱신한다. 상세는 [협업 프로세스 초안](../04-tasks/collaboration-workflow.md)을 참조한다.

템플릿 변경 시 기존 프로젝트는 고정 버전을 유지하고 변경 내용을 보고 명시적으로 적용한다. 같은 버전의 템플릿에서는 필수 정보의 의미를 프로젝트마다 다르게 바꾸지 않는다.

## 7. 규칙 중심 작성 방식 — 후속 제안

2026-09-09 사용자 확인: AGENTS.md를 메인 진입점으로 두고 상세 Markdown 규칙을 분리하는 방향을 승인했다. 수동 템플릿 복사를 필수로 하지 않는다. 아래 파일명은 제안이며 ID 문법·승인 범위·검증 방법·패키지 설치 방식의 세부 설계가 모두 승인된 것은 아니다.

사용자는 빈 템플릿을 복사하기보다 AGENTS.md를 메인으로 두고 상세 Markdown 규칙을 참조해 에이전트가 작성하는 방식을 제안했다. 공통 양식이라는 목표는 유지하되 배포·사용의 중심을 복사용 파일에서 작성 규칙으로 바꾼다. 실제 파일 배치와 내용은 검토 단계다.

### 파일 역할 제안

- `AGENTS.md`: 짧은 공통 원칙, 작업별 필수 읽기 경로, 규칙 충돌 처리, 검증 진입점. 세부 규칙을 다시 요약해 두 개의 정본으로 만들지 않는다.
- `rules/spec-writing.md`: 4영역과 유형별 필수 내용, 적용 조건, 분리 기준, 사람의 읽기 기준.
- `rules/identity-and-references.md`: ID 범위·발급·유지, 메타데이터, 참조 문법, 삭제/누락/중복 처리.
- `rules/sdd-workflow.md`: 요구→설계→작업→구현→검증, 준비 조건, 명세 변경과 재검토 기준.
- `rules/github-collaboration.md`: Issue 연결·배정, Project 상태, 브랜치·PR·리뷰·완료/취소 처리.
- `rules/validation.md`: 필수 필드·ID·참조·작업 연결 검사, 검증 실행 시점, 실패 처리. 검사기의 실제 구현 상태를 명시한다.
- `rules/project-settings.md`: 해당 프로젝트의 목표 문서·저장소·기준 브랜치·GitHub Project·실행/검증 명령 등 프로젝트별 값. 공통 규칙을 복사하지 않는다.

위 경로 중 `rules/spec-writing.md`와 `rules/validation.md`는 2026-09-10에 실제로 만들어 활성 규칙으로 전환했다. 나머지 경로는 여전히 구조 제안이다. 현재 협업 프로세스 초안은 후속 확정 시 해당 규칙으로 이관하고 기존 문서는 링크만 남기는 방식으로 중복을 피한다.

### 읽기와 배포 제안

작업 시작 시 AGENTS.md와 프로젝트별 설정을 읽고, 문서 작성은 작성/ID 규칙, 구현은 SDD/GitHub/검증 규칙처럼 필요한 파일을 명시적으로 읽도록 안내한다. 링크만 있다고 상세 내용이 항상 로드되었다고 가정하지 않는다.

조직 공통 규칙은 한 원본에서 버전 관리하고 각 프로젝트에는 고정 버전을 자동 설치/갱신하는 방식을 검토한다. 사용자가 매번 복사할 필요는 없지만 프로젝트가 읽을 수 있는 규칙 파일은 제공되어야 한다. 설치 방식은 미정이며 매번 원격 최신 규칙을 읽는 방식은 재현성과 가용성 때문에 기본으로 권하지 않는다.

프로젝트 설정은 공통 규칙이 허용한 값과 명시적 예외만 담는다. 현재 사용자의 명시적 요청은 우선하며, 근거 없이 프로젝트 지침이 모든 공통 규칙을 덮어쓴다고 가정하지 않는다. 충돌 시 어느 규칙이 다른지 드러내고 조용히 선택하지 않는다.

예시는 이해를 돕는 참고로 제공할 수 있지만 복사는 필수가 아니다. 문서의 필수 정보·ID·참조가 규칙을 만족하는지 검증해야 한다. 자연어 지침만으로 모든 에이전트가 동일하게 준수한다고 보장하지 않는다. 기계가 검사할 필드/허용 값은 후속 스키마 한 곳에서 정의하고 안내 문서에서 참조한다.

## 8. 이번 검토 범위

AGENTS.md 진입점과 상세 규칙 분리 방향은 확정했다. 다음으로 사람/에이전트의 역할과 승인 경계, ID·메타데이터 규약, GitHub 협업 세부 규칙, 읽기 화면을 구체화한다. 이번 결과물은 구성안과 축약 예시이며 파서·검증기·규칙 패키지를 구현한 것은 아니다.
