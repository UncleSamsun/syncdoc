# 화면 명세

색·서체·간격·컴포넌트·접근성은 [공통 UI 규칙](ui-conventions.md)을 따르고 여기서 반복하지 않는다. 근거 요구는 [MVP 기능과 인수 기준](../01-prd/mvp-scope.md), 응답 구조는 [MVP API 계약](../03-tech-spec/api-spec.md)이다. 요구 ID는 REQ-001 ~ REQ-008, 작업 ID는 TASK-001 ~ TASK-008, 계약 ID는 API-001 ~ API-025로 그 문서들에서 읽는다. 계약은 메서드·경로가 아니라 ID로 가리킨다. 경로는 구현 중에 바뀔 수 있다.

이 문서에 있는 화면만 구현한다. 문구는 적힌 그대로 쓴다.

레이아웃을 눈으로 확인할 때는 [화면 정의 페이지](screens/README.md)를 연다. 그 페이지는 시각 참조이고 이 문서가 정본이다.

## 경로

| 경로 | 화면 |
|---|---|
| `/login` | UI-005 |
| `/projects` | UI-001 |
| `/projects/:projectId` | UI-002로 이동 |
| `/projects/:projectId/overview` | UI-002 |
| `/projects/:projectId/documents` | UI-003의 목록 상태 |
| `/projects/:projectId/documents/:documentId` | UI-003 |
| `/projects/:projectId/tasks?status=&assignee=` | UI-014 |
| `/projects/:projectId/checklist` | UI-013 |
| `/projects/:projectId/search?q=` | UI-004 |
| `/projects/:projectId/settings` | UI-015 |

모든 화면은 URL로 직접 열 수 있고 새로 고침 후 같은 상태로 복원된다. `snapshotId` 질의값이 붙은 URL도 열 수 있으며 열 때 현재 사용자 권한을 다시 확인한다.

## 화면과 계약

화면이 어느 계약을 부르는지는 여기 한 곳에 둔다. 계약의 입력·응답·오류는 [MVP API 계약](../03-tech-spec/api-spec.md)에 있고 여기서 반복하지 않는다. 표에 없는 계약을 화면에서 부르지 않는다.

| 화면 | 부르는 계약 |
|---|---|
| UI-000 공통 셸 | API-003, API-010, API-011, API-012, API-013, API-014, API-015 |
| UI-001 프로젝트 홈 | API-008, API-009, API-010, API-011, API-012 |
| UI-002 현황 | API-015, API-016 |
| UI-003 문서 본문 | API-017, API-018, API-020 |
| UI-013 산출물 체크리스트 | API-025 |
| UI-014 작업 전체 목록 | API-016 |
| UI-015 연결 설정 | API-011, API-012 |
| UI-004 검색 | API-019 |
| UI-005 로그인 | API-001, API-002 |
| UI-006 미초대 계정 | API-002, API-003 |
| UI-007 첫 동기화 대기 | API-014, API-017, API-018 |
| UI-008 갱신 실패 · 오래된 정보 | API-014, API-015 |
| UI-009 Project 조회 불가 | API-015 |
| UI-010 집계 미완 | API-015 |
| UI-011 없는 문서 · 권한 없음 | API-018 |
| UI-012 회수된 snapshot | API-017, API-018 |

사이드바의 문서·작업 건수는 셸이 API-015의 `counts`에서 읽는다. 초대 관리(API-005·API-006·API-007)를 부르는 화면은 MVP에 없다. 상태 확인(API-022·API-023)과 webhook 수신(API-021)은 화면이 부르지 않는다.

## UI-000 공통 셸

**연결 요구:** REQ-002, REQ-006, REQ-007 · **관련 작업:** TASK-006

**진입:** 세션이 있고 열람 가능한 프로젝트가 하나 이상일 때 모든 화면. **종료:** 로그아웃 시 UI-005.

**레이아웃:** 상단바 50 + 사이드바 248 + 본문.

상단바는 좌측부터 제품 표식, 프로젝트 스위처(`저장소 전체이름`), 브랜치 스위처(가지 아이콘 + 브랜치 이름), 문서 경로 글자를 두고 우측에 동기화 칩 · 연결 설정 톱니바퀴(UI-015) · 계정 표식을 둔다. 제품 표식은 UI-001 프로젝트 홈으로 가는 링크다.

사이드바는 이동 항목 넷(현황 · 작업(건수) · 산출물(오류 건수) · 검색) 아래에 `문서` 섹션 머리(오른쪽에 문서 건수)와 문서 트리를 둔다. `문서` 섹션 머리는 13px, 그 아래 폴더 줄은 12px로 두어 머리가 한 단 크다. 머리와 첫 폴더 줄 사이는 1px로 붙여 한 묶음으로 읽히게 하고, 대신 머리 위쪽으로 14px을 띄워 위쪽 이동 항목과 구분한다. 사이드바의 모든 건수(이동 항목 · `문서` 머리 · 폴더 줄)는 사이드바 안쪽 오른쪽에서 같은 7px 지점에 오른쪽 정렬해 한 열을 이룬다. 자릿수가 달라도 끝이 어긋나지 않게 `tabular-nums`를 적용한다. 트리는 셸의 일부이므로 현황·작업·산출물·검색·문서 어느 화면에서도 같은 자리에 그대로 있고, 화면이 바뀔 때 사이드바가 다른 내용으로 교체되지 않는다. `문서` 섹션 머리에는 동작 버튼을 두지 않는다. 트리 자체의 규칙은 UI-003의 문서 트리 절을 따른다.

프로젝트를 고르고 저장소를 연결하는 일은 사이드바가 아니라 UI-001이 전담한다. 사이드바에 프로젝트 관련 이동 항목이나 동작 버튼을 두지 않는다.

**사용자 행동:** 프로젝트 전환, 문서 기준 브랜치 전환, 연결 설정 열기, 프로젝트 홈으로 이동, 문서 선택, 화면 이동, 로그아웃.

### 브랜치 전환

- 문서 기준 브랜치의 기본값은 `main`이다. 다른 값을 기본값으로 미리 채우지 않는다.
- 브랜치 스위처는 저장소에서 읽을 수 있는 브랜치만 나열한다. 이름을 직접 입력하는 수단을 두지 않는다.
- 바꾸면 API-012에 `branch`와 `expectedVersion`을 보내고 새 수집을 예약한다. 이 요청은 CSRF 토큰을 함께 보낸다.
- 새 수집이 끝날 때까지 이전 브랜치의 snapshot을 계속 보여주고, 동기화 칩에 `<브랜치> 수집 중`을 표시한다. 두 브랜치의 문서를 섞어 보여주지 않는다.
- 연결자 또는 서비스 관리자가 아니면 스위처를 점선 읽기 전용으로 두고 현재 브랜치만 표시한다. 목록을 열지 않는다.
- 버전 충돌(409)이면 `다른 사용자가 연결 설정을 먼저 바꿨습니다. 최신 설정을 불러옵니다.`를 표시하고 현재 설정을 다시 읽는다.

**상태:**
- 동기화 칩은 마지막 성공 시각을 UTC로 표시하고, 정상일 때 초록 형식을 쓴다.
- 수집이 실패한 동안 칩은 같은 형식의 빨강으로 바뀌고 다음 재시도 시각을 표시한다.
- 첫 수집 전에는 칩에 `첫 수집 대기`를 표시한다.
- 문서·작업 건수는 마지막 정상 snapshot 기준이며, 집계가 미완이면 건수 뒤에 확정 아님 칩을 붙인다.

### 갱신

화면을 보는 동안 20초 간격으로 API-014를 확인한다. 새 snapshot이 게시되면 현황·목록 화면은 조용히 갱신하고, 문서 본문을 열고 있을 때는 본문을 교체하지 않고 상단에 `새 버전이 게시되었습니다 · 새로 고치기` 배너를 띄운다. 읽던 위치를 임의로 잃게 하지 않는다.

**검증:** 프로젝트를 전환해도 이전 프로젝트의 건수·목록이 남지 않는다. 수집 실패 중에도 셸이 마지막 정상 값을 유지한다. 브랜치를 바꾸는 동안 이전 브랜치의 문서가 유지되고, 수집이 끝난 뒤에만 새 브랜치 문서로 바뀐다. 연결 권한이 없는 계정에서는 브랜치를 바꿀 수 없다.

## UI-001 프로젝트 홈

**연결 요구:** REQ-002, REQ-007 · **관련 작업:** TASK-003

**진입:** 세션이 있고 열람 가능한 프로젝트가 없을 때, 제품 표식을 눌렀을 때, 프로젝트 스위처에서 프로젝트 홈을 골랐을 때. 프로젝트가 있어도 언제든 들어올 수 있다. **종료:** 프로젝트를 열면 그 프로젝트의 UI-002, 연결 성공 시에도 UI-002.

**레이아웃:** 상단바 + 단일 본문 열. 사이드바를 두지 않는다 — 아직 프로젝트 맥락이 없다. 제목 `프로젝트 홈`과 우측에 주 버튼 `저장소 연결`, 안내 한 줄, 연결된 프로젝트 목록, 저장소 연결 양식 순서로 쌓는다. 연결 양식은 주 버튼의 펼친 상태다.

목록 항목에는 상태 점, 저장소 전체이름(고정폭), `브랜치 · 문서경로 · snapshot id · 마지막 성공 시각`, 문서 건수 칩, 열기 버튼을 둔다.

연결 양식 필드는 저장소 · 기준 브랜치 · 문서 경로 · GitHub Project 넷이다. 기본값은 브랜치 `main`, 문서 경로 `docs`를 미리 채운다. 브랜치 필드 아래에 연결 후 상단바에서 바꿀 수 있다는 도움말을 둔다.

**사용자 행동:** 프로젝트 열기, 저장소 선택, 브랜치·문서 경로 선택, GitHub Project 선택 또는 연결하지 않음, 연결, 취소.

**상태:**
- 후보 저장소는 API-008 결과만 나열한다. 임의 URL·로컬 경로를 입력하는 수단을 두지 않는다.
- 후보가 없으면 `연결할 수 있는 저장소가 없습니다`와 함께, 앱과 계정 양쪽에서 접근 가능한 저장소만 연결할 수 있다는 안내를 둔다.
- 브랜치나 문서 경로가 실제로 없으면 해당 필드 아래에 오류를 붙이고 연결을 진행하지 않는다. 문구는 `이 브랜치에 <경로> 경로가 없습니다. 실제 경로를 선택하세요.`
- 중복 연결(409)은 오류로 보이지 않게 하고 해당 항목을 `이미 연결됨`으로 표시하며 열기 버튼을 준다.
- GitHub Project를 연결하지 않으면 문서와 Issue·PR 현황만 제공한다는 도움말을 둔다.
- 연결 직후 목록 항목은 `첫 수집 대기` 상태로 표시한다.
- 연결 권한이 없는 프로젝트의 설정 화면은 열지 않는다.

**검증:** 같은 저장소를 두 번 연결해도 프로젝트가 늘지 않는다. 없는 브랜치·경로로는 연결이 성공하지 않는다. 다른 사용자가 연결한 프로젝트의 설정을 바꿀 수 없다.

## UI-002 현황

**연결 요구:** REQ-003, REQ-006, REQ-007 · **관련 작업:** TASK-007

**진입:** 사이드바 현황, 프로젝트 열기, 프로젝트 전환. **종료:** 문서·작업·검색 화면 이동.

**레이아웃:** 셸 본문에 12열 격자. 위에서 아래로

1. 화면 머리 — 제목 `현황`, `snapshot id · revision`, 우측에 `지금 동기화` 버튼
2. 지표 카드 4장, 각 3열 — 동기화 · 작업 완료 · Project 완료율 · 문서
3. 상태별 건수 카드, 12열 — 스택바 + 범례
4. 작업 · Issue 매핑 표, 12열
5. 최근 변경 표, 12열

### 지표 카드 규칙

- 동기화 — 정상이면 마지막 성공 시각, 실패 중이면 `오래된 정보`와 `마지막 성공 <시각> · 실패 <시각>`, 오류 코드를 표시한다. 실패 중에는 카드가 실패 배경·테두리·글자색을 쓴다.
- 작업 완료 — `완료건수 / 분모` 형태로 쓰고 아래에 `상태 명시 <n>건 기준 · 취소 <n>건 제외`를 적는다. 분모 없이 숫자만 두지 않는다.
- Project 완료율 — `projectAccess`가 `unavailable`이면 점선 테두리와 `조회 불가`를 쓰고 `projectAccess: unavailable`, `추정하지 않습니다`를 적는다. 0%나 빈 막대를 그리지 않는다.
- 문서 — 마지막 정상 snapshot의 문서 건수.

### 상태별 건수 카드 규칙

세그먼트는 미착수 · 진행 · 리뷰 · 완료 · Issue 미등록 · 취소 순서로 두고 범례에 이름과 건수를 함께 적는다. 취소 세그먼트에는 `분모 제외`를 적는다. `partial`이 참이면 카드 라벨 옆에 `수집 중 · 확정 아님` 칩을 붙인다. 분모가 0이면 막대를 그리지 않고 `계산 대상 없음`을 표시한다.

### 작업 표 규칙

열은 TASK · 제목 · Issue · 상태 · PR · 담당이다.
- 상태는 점 + 글자로 표시한다.
- 취소된 작업은 흐린 글자와 취소선으로 두고 상태 칸에 해치 칩 `취소 · 제외`를 쓴다.
- Issue가 없는 작업은 Issue 칸에 `—`, 상태 칸에 점선 칩 `Issue 미등록`을 쓴다.
- PR이 여러 개면 번호를 모두 나열한다. PR 개수를 완료 건수로 세지 않는다.
- 담당은 명시적으로 배정된 계정만 표시하고 없으면 `미배정`으로 둔다. 최근 커밋 작성자를 담당으로 쓰지 않는다.
- 표 머리에 `<표시건수>건 중 <전체>건`을 적고 그 옆에 `전체 보기`를 두어 UI-014로 이어 본다. 여기서는 첫 20건만 보인다.
- 배포 상태는 `미수집`으로 표시한다. dev 개발 완료와 main 릴리스를 같은 값으로 쓰지 않는다.

**사용자 행동:** 지금 동기화 요청, 작업 행에서 Issue 열기, 최근 변경 항목에서 문서 열기, 작업 전체 목록 열기.

**상태:** 불러오는 중에는 카드와 표 자리에 골격 로딩을 둔다. 첫 수집 전에는 UI-007, 수집 실패 중에는 UI-008, Project 조회 불가는 UI-009, 집계 미완은 UI-010의 표현을 쓴다.

**검증:** 취소가 완료에 포함되지 않는다. Issue 미등록 작업이 목록에서 사라지지 않는다. Project 권한이 없을 때 완료율이 0%로 보이지 않는다. `partial`이 참일 때 완료율이 확정된 값처럼 보이지 않는다. 수집 실패 후에도 마지막 정상 값이 유지되고 기준 시각이 함께 보인다.

## UI-003 문서 본문

**연결 요구:** REQ-004, REQ-005, REQ-007 · **관련 작업:** TASK-006

**진입:** 사이드바 문서, 최근 변경 항목, 검색 결과, 문서 간 링크. **종료:** 다른 문서, 현황, 검색.

**레이아웃:** 사이드바는 UI-000과 똑같이 두고(트리에서 현재 문서만 활성 표시) 본문만 좌측 본문 + 우측 목차(196) 두 열로 바뀐다.

### 문서 트리

- 문서 경로의 폴더를 그대로 계층으로 보여준다. 폴더를 화면에서 임의로 묶거나 펼쳐서 한 줄로 만들지 않는다.
- 폴더 줄은 높이 30, 펼침 표식(11px 화살표) + 폴더 아이콘(14px) + 폴더 이름 + 우측 문서 건수 순서다. 폴더 사이에 구분선을 두지 않는다. 폴더 경계는 폴더 아이콘·대문자 라벨과 자식 묶음 아래 여백으로 나눈다.
- 폴더 아이콘은 접힘·펼침에 따라 바꾸지 않는다. 열림 여부는 펼침 표식이 전달한다. 문서 항목에는 아이콘을 붙이지 않는다.
- 폴더는 접을 수 있다. 접힘·펼침 상태를 프로젝트별로 브라우저에 저장해 다음 방문에도 유지한다. 저장된 값이 없거나 읽을 수 없으면 모두 펼친 상태로 시작한다.
- 열고 있는 문서가 든 폴더는 항상 펼치고, 폴더 이름과 아이콘의 글자 색만 `--ink`로 한 단 올린다. 굵기는 올리지 않는다.
- 자식 문서 항목은 왼쪽 안내선으로 들여쓴다. 활성 문서는 흰 바탕과 테두리로 표시한다.
- 폴더 줄과 문서 항목은 키보드로 이동·펼침이 가능해야 한다. 펼침 표식만으로 상태를 전달하지 않고 펼침 여부를 보조 기술이 읽을 수 있게 표시한다.

본문은 제목, 메타 줄(`파일 경로 · revision · snapshot id`), 구분선, 내용 순서다. 본문 폭은 68자에서 끊는다.

우측 목차는 `headings` 배열로 만들고 현재 위치를 표시한다. 목차 아래에 `warnings`를 `경고 <n>` 묶음으로 모은다. 경고를 본문 사이에 끼우지 않는다.

### 내용 규칙

- 본문은 `html` 필드를 그대로 표시한다. 화면에서 원문 Markdown을 다시 해석하지 않는다.
- 표는 머리 행을 고정 배경으로 두고 자기 컨테이너에서 가로 스크롤한다.
- 문서 안 링크는 `links`가 변환한 서비스 경로만 사용한다. 같은 snapshot의 문서·첨부로 이동한다.
- 이미지는 API-020으로 불러오고 `snapshotId`를 함께 보낸다.
- 다이어그램은 `diagrams[]`의 원문을 제한된 Mermaid에 넘겨 각 블록 자리에 그린다. 지원 유형은 흐름도 · 시퀀스 · ERD · 클래스 · 상태도다.
- 각 다이어그램 위에 `diagram <n> · <유형>` 머리와 `원문 보기` 버튼을 둔다.
- 다이어그램 렌더 실패·크기 초과·시간 초과는 해당 블록만 오류 상자로 바꾸고 `원문 보기 (<크기>)` 버튼을 준다. 문구는 `이 블록만 표시되지 않습니다. 문서의 나머지는 그대로 읽을 수 있습니다.` 나머지 본문은 계속 읽을 수 있어야 한다.
- 블록당 20 KB, 문서당 20개, 렌더 3초를 넘기면 그리지 않고 원문 보기로 대체한다.

**사용자 행동:** 문서 선택, 폴더 접기·펼치기, 목차 항목으로 이동, 문서 내 링크 이동, 다이어그램 원문 보기, 표 가로 스크롤.

**상태:** 불러오는 중 골격 로딩. 첫 수집 전에는 UI-007. 문서가 없거나 권한이 없으면 UI-011. `snapshotId`가 회수되었으면 UI-012. 응답이 422면 `이 문서를 표시할 수 없습니다`와 함께 문서 목록으로 돌아가는 버튼을 둔다.

**검증:** 폴더를 접었다 펴고 새로 고쳐도 상태가 유지되며, 접힌 폴더의 문서를 링크로 열면 그 폴더가 펼쳐진다. 다섯 다이어그램 유형이 모두 그려진다. 잘못된 문법·과대 입력·시간 초과가 해당 블록에만 표시되고 문서는 읽힌다. 표·한글 제목·명시 앵커·상대 링크·접기가 정상 표시된다. 같은 snapshot 안에서 문서 간 이동이 유지된다. 권한 없는 이미지와 과거 snapshot 직접 요청이 표시되지 않는다.

### 링크 표시

- 같은 게시본의 문서·첨부 링크는 서비스 안에서 이동한다.
- 수집 대상 밖 파일을 가리키는 링크(`kind`가 `source`)는 수집 시점 GitHub 주소로 **새 탭에서** 열린다. 서비스 안 이동과 구분되는 표식을 붙이고, 어디로 가는지 누르기 전에 알 수 있게 한다. 읽던 자리를 잃지 않게 하려는 것이다.
- 열 수 없는 링크는 링크로 보이지 않는다. 글자로만 남긴다. 누를 수 있게 보이는데 아무 데도 가지 않는 것이 가장 나쁘다.

## UI-004 검색

**연결 요구:** REQ-004, REQ-007 · **관련 작업:** TASK-007

**진입:** 사이드바 검색. **종료:** 결과 선택 시 UI-003.

**레이아웃:** 검색 입력 한 줄과 결과 목록. 입력 우측에 `현재 프로젝트 · <n>건`을 표시한다. 결과 항목은 문서 제목, `파일 경로 · 앵커`, 발췌 순서로 두고 검색어 부분을 표시한다.

**사용자 행동:** 검색어 입력, 결과 선택.

**상태:**
- 검색어는 1~200자다. 200자를 넘기면 입력을 조용히 잘라내지 않고 길이를 알린다.

- 첫 수집 전에는 검색을 실행하지 않고 UI-007을 표시한다.

**검증:** 다른 프로젝트의 문서가 결과에 나오지 않는다. 권한이 없는 문서가 결과·발췌에 나오지 않는다. 결과를 선택하면 같은 snapshot의 해당 위치로 이동한다.

**진입:** 이전 정상 snapshot이 있고 이후 수집이 실패했을 때. **종료:** 수집이 다시 성공하면 배너가 사라진다.

**레이아웃:** 화면 상단 실패 배너 `<시각> 기준 정보입니다 · 이후 갱신 실패`와 우측 `재시도 <시각>`, 본문 안내 `아래 내용은 마지막으로 성공한 snapshot입니다. 실패한 수집이 이 데이터를 덮어쓰지 않았습니다.`, 오류 코드.

마지막 정상 데이터를 계속 보여주되 최신이라고 쓰지 않는다. 오류 문구에 토큰·서버 내부 경로를 넣지 않는다. 첫 수집이 실패했고 이전 정상 snapshot이 없으면 빈 문서 목록과 이 배너를 함께 표시한다.

**검증:** 마지막 정상 snapshot의 내용이 그대로 보이고 기준 시각이 함께 보인다. 실패한 수집이 이전 데이터를 덮어쓰지 않는다. 오류 문구에 토큰과 내부 경로가 없다.

**진입:** `projectAccess`가 `unavailable` 또는 `not_connected`일 때 Project 완료율 자리. **종료:** 권한이 확인되거나 Project를 연결하면 완료율로 대체된다.

**레이아웃:** 점선 상자에 `조회 불가`, 우측에 `progress: null`, 본문 `이 계정으로 연결된 GitHub Project를 조회할 수 없습니다. Project 기반 완료율은 표시하지 않습니다. 문서와 Issue 현황은 그대로 사용할 수 있습니다.`

`not_connected`는 같은 자리에 `연결 안 함`과 `이 프로젝트에 GitHub Project를 연결하지 않았습니다. 연결하면 Project 기반 완료율을 함께 보여줍니다.`를 쓴다. 할 일이 다르므로 권한 없음과 같은 문구를 쓰지 않는다.

**검증:** 완료율 자리에 0%나 빈 막대가 나타나지 않는다. Project를 조회할 수 없는 동안에도 문서·Issue 현황이 계속 보인다.

## UI-013 산출물 체크리스트

**연결 요구:** REQ-008 · **관련 작업:** TASK-004

2026-09-22 사용자 확정으로 별도 화면이다. [정의 파일 설계](../03-tech-spec/spec-format-proposal.md)는 현황 화면 안의 구획을 제안했지만, 수집 상태·진행률과 규약 준수는 성격이 다른 정보이고 현황 화면이 이미 카드와 작업 표로 길다.

**진입:** 사이드바 `산출물`. **종료:** 다른 이동 항목, 오류가 가리키는 문서 본문(UI-003).

**레이아웃:** 셸 본문에 위에서 아래로

1. 화면 머리 — 제목 `산출물 체크리스트`, `snapshot id · revision`, 우측에 상태 칩
2. 요약 줄 — `적용 <n>종 · 문서 <n>건 · 오류 <n>건 · 미작성 <n>종`
3. 종류 표 — 종류마다 한 행. 열은 종류 · 적용 · 상태 · 문서 · 오류다

### 상태 문구

[검증 규칙](../../rules/validation.md) §7의 네 값을 그대로 쓴다. 다른 말로 바꾸지 않는다.

| 값 | 화면 문구 | 뜻 |
|---|---|---|
| `pass` | `통과` | 검사 대상이 있고 오류가 없다 |
| `error` | `오류 <n>건` | 오류가 하나 이상이다 |
| `pending` | `미작성` | `보류`로 정한 종류의 문서가 아직 없다. 오류가 아니다 |
| `unchecked` | `미검사` | 규칙 파일을 읽지 못했다 |

`미검사`를 `통과`로 바꾸지 않는다. 오류 0건이라는 이유로도 바꾸지 않는다. `미작성`과 `오류`를 같은 색·같은 문구로 두지 않는다.

### 종류에 붙지 않는 오류

문서 식별·분류 오류(`id`가 없거나 형식이 틀리거나 중복, `type`이 없거나 허용 값이 아님)와 적용 Spec 표 자체의 오류는 어느 종류에도 속하지 않는다. 종류 표 **위에** 따로 목록으로 둔다. 종류 안에 숨기면 어느 종류를 펼쳐야 보이는지 알 수 없다.

### 종류 표 규칙

- 종류 이름은 정의 파일의 `name`을 쓴다. 화면에서 다시 짓지 않는다.
- `적용` 칸은 `적용`·`보류`·`미적용`이다. `보류`·`미적용`은 적용 Spec 표의 사유를 같은 칸에 함께 보인다. 사유가 비어 있으면 그 자체가 오류이므로 오류로 표시한다.
- `미적용` 종류는 흐린 글자로 두고 상태 칸을 비운다. 검사하지 않은 것을 통과로 보이게 하지 않는다.
- 행을 펼치면 그 종류의 문서 목록과 오류 목록이 나온다. 오류는 `경로:줄`과 내용을 한 줄에 둔다. 줄 번호가 없는 오류(문서 자체가 없는 C1)는 경로 자리에 `문서 없음`을 쓴다.
- 오류의 경로는 같은 게시본의 문서 본문(UI-003)으로 이어진다. 줄이 있으면 그 자리의 앵커까지 간다.
- 기준을 고치는 조작을 두지 않는다. 정의 파일과 적용 Spec 표는 저장소에서 고친다. 이 화면에 편집·해제·무시 버튼을 만들지 않는다.

### 미검사 화면

`unchecked`이면 표 대신 안내를 둔다. 문구는 이유에 따라 다르다.

- `DEFINITION_MISSING` — `규칙 정의 파일이 없어 검사하지 않았습니다` · `저장소 루트의 rules/spec-format.json을 읽지 못했습니다.`
- `APPLY_TABLE_MISSING` — `적용 Spec 표가 없어 검사하지 않았습니다` · `저장소 루트의 rules/project-settings.md에서 적용 Spec 표를 읽지 못했습니다.`
- `NO_DOCUMENTS` — `검사할 문서가 없어 검사하지 않았습니다` · `이 게시본에 문서가 없습니다.`
- `NOT_COMPUTED` — `이 게시본은 규약 판정 전에 만들어졌습니다` · `다음 수집에서 다시 만들어집니다.`

둘 다 `이 프로젝트는 규약 검사를 적용하지 않습니다`처럼 판정한 것처럼 쓰지 않는다. 읽지 못한 것과 지킨 것은 다르다.

### 잘린 결과

`truncated`가 참이면 표 아래에 `오류가 많아 일부만 보여줍니다 · 저장소에서 확인하세요`를 둔다. 다음 쪽 단추를 두지 않는다.

**상태:** 첫 수집 전에는 UI-007 첫 수집 대기를 그대로 쓴다. 회수된 snapshot을 지정하면 UI-012다. 볼 수 없는 프로젝트는 UI-011과 같은 화면이다.

**검증:** 미검사가 통과로 보이지 않는다. 미작성과 오류가 구분된다. 보류·미적용의 사유가 화면에 함께 보이고 사유 없는 항목은 오류로 보인다. 오류에서 문서 본문의 그 자리로 이동한다. 이 화면에서 기준을 고치는 조작이 없다.

## UI-014 작업 전체 목록

**연결 요구:** REQ-003 · **관련 작업:** TASK-009

현황(UI-002)의 작업 표는 첫 20건이다. 20건을 넘는 프로젝트에서 나머지를 볼 곳이 이 화면이다. 계약은 API-016이며 새로 만들지 않는다.

**진입:** 사이드바 `작업`, 현황 작업 표의 `전체 보기`. **종료:** 작업이 가리키는 문서(UI-003), Issue.

**레이아웃:** 셸 본문에 위에서 아래로

1. 화면 머리 — 제목 `작업`, `snapshot id · revision`, 건수 `<표시건수>건 중 <전체>건`
2. 거르기 줄 — 상태 고르기와 담당 고르기
3. 작업 표 — 열은 현황과 같다

### 표 규칙

열과 표시 규칙은 UI-002의 작업 표 규칙을 그대로 따른다. 여기서 다시 정하지 않는다. 같은 자료를 두 화면이 다르게 보여주면 어느 쪽이 맞는지 알 수 없다.

### 거르기 규칙

- 상태와 담당은 URL 질의값(`status`, `assignee`)으로 남는다. 새로 고쳐도 같은 목록이고, 그 주소를 그대로 전달할 수 있다.
- 거른 상태에서는 건수에 `걸러진 <n>건 / 전체 <n>건`을 적는다. 거르기 때문에 줄어든 것을 전체가 줄어든 것으로 읽히게 하지 않는다.
- 담당 고르기의 후보는 목록에 실제로 있는 담당자뿐이다. 없는 사람을 고를 수 있게 두지 않는다.
- 거르기를 지우는 수단을 함께 둔다. 거른 채로 막히지 않게 한다.
- 취소된 작업은 거르기와 무관하게 분모에서 빠진다는 표시를 유지한다.

**상태:** 첫 수집 전에는 UI-007을 쓴다. 거른 결과가 없으면 `조건에 맞는 작업이 없습니다`와 거르기를 지우는 수단을 둔다 — 작업이 하나도 없는 것과 다른 문구다. 볼 수 없는 프로젝트는 UI-011과 같다.

**사용자 행동:** 상태·담당으로 거르기, 거르기 지우기, 작업이 가리키는 문서 열기, Issue 열기.

**검증:** 20건을 넘는 게시본에서 전부 볼 수 있다. 거른 결과와 전체 건수가 구분된다. 취소가 완료로 세어지지 않고 Issue 미등록 작업이 목록에서 사라지지 않는다. 거른 주소를 새로 고쳐도 같은 목록이다. 이 화면에서 작업 상태를 바꾸는 조작이 없다 — 상태는 GitHub가 정본이다.

## UI-015 연결 설정

**연결 요구:** REQ-002 · **관련 작업:** TASK-012

연결한 저장소의 문서 경로와 GitHub Project 연결을 바꾼다. 기준 브랜치는 상단바가 맡으므로 여기서 또 두지 않는다 — 같은 값을 두 곳에서 바꾸게 하면 어느 쪽이 방금 쓴 값인지 알 수 없다.

**진입:** 상단바의 연결 설정. **종료:** 저장 후 같은 화면에 머무르거나 현황으로 이동.

**레이아웃:** 셸 본문에 위에서 아래로

1. 화면 머리 — 제목 `연결 설정`, `저장소 전체이름`
2. 바꿀 수 없는 값 — 저장소, 기준 브랜치. 각각 왜 여기서 못 바꾸는지 한 줄로 적는다
3. 문서 경로 입력과 저장
4. GitHub Project 연결 입력과 저장·해제

### 규칙

- 연결자 또는 서비스 관리자만 바꿀 수 있다. 그 외에는 입력을 읽기 전용으로 두고 `연결한 사람 또는 서비스 관리자만 바꿀 수 있습니다.`를 함께 적는다. 누를 수 있게 보이는데 거절당하는 단추를 두지 않는다.
- 저장은 API-012에 `expectedVersion`과 CSRF 토큰을 함께 보낸다.
- 입력 오류(422)는 그 칸 아래에 서버가 준 문구 그대로 둔다. 다른 말로 바꾸지 않는다.
- 버전 충돌(409)이면 `다른 사용자가 연결 설정을 먼저 바꿨습니다. 최신 설정을 불러옵니다.`를 표시하고 현재 설정을 다시 읽는다. 사용자가 쓰던 값을 조용히 덮어써 보내지 않는다.
- 문서 경로를 바꾸면 새 수집이 돈다. 끝날 때까지 이전 게시본을 계속 보여주고, 상단바 칩이 수집 중임을 알린다. 두 경로의 문서를 섞지 않는다.
- GitHub Project를 연결하지 않으면 문서와 Issue·PR 현황만 제공한다는 것을 적는다. 해제도 같은 화면에서 한다.
- **저장소 연결을 끊는 수단을 두지 않는다.** 그 계약이 없다. 게시본·작업·Issue 사본을 어떻게 할지 정하지 않은 채로 끊는 단추만 두면 되돌릴 수 없는 일이 된다.

**상태:** 저장 중에는 단추를 잠근다. 저장에 성공하면 `저장했습니다`를 표시하고 바뀐 값을 다시 읽어 보여준다. 볼 수 없는 프로젝트는 UI-011과 같다.

**사용자 행동:** 문서 경로 바꾸기, GitHub Project 연결·해제.

**검증:** 권한이 없는 계정에는 바꾸는 수단이 보이지 않는다. 저장이 `expectedVersion`을 함께 보낸다. 409에서 사용자가 쓰던 값을 덮어써 보내지 않는다. 422 문구가 그 칸 아래에 그대로 나온다. 연결을 끊는 수단이 없다.

## 좁은 화면

720px 이하에서 현황의 12열 격자는 1열로 쌓고, 작업 표는 행마다 TASK·제목·상태·Issue를 담은 카드 목록으로 바꾼다. 문서 화면의 목차는 본문 위 접힌 목록으로 옮긴다. 어느 화면에서도 페이지 본문이 가로로 밀리지 않는다.

## fixture 표시

백엔드가 없는 동안 화면은 API 계약과 같은 구조의 fixture를 쓴다. fixture로 채운 화면에는 `샘플 데이터`를 화면에서 확인할 수 있게 표시하고, 실제 GitHub 조회 결과로 보이게 하지 않는다. fixture에는 실행 가능한 script를 넣지 않는다.

## 이 문서를 고쳐야 하는 변경

새 화면·새 컴포넌트·새 색이 필요할 때, 상태 문구를 바꿀 때, 위 검증 항목을 바꿀 때는 구현 전에 이 문서와 [공통 UI 규칙](ui-conventions.md)을 먼저 고친다. 화면이 명세보다 앞서 나가게 두지 않는다.
