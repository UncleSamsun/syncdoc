# MVP 구현 구조 제안

기술 구성은 확정했고 상세 설계와 구현은 아직 하지 않았다.

## 고정된 사용자 흐름

상세 검토 문서: [기능·인수 기준](../01-prd/mvp-scope.md), [API 계약](api-spec.md), [데이터 모델](data-model.md), [구현 작업계획](../04-tasks/implementation-plan.md). 기술 구성은 확정되었고 이 문서들의 정량 제한·초대 방법·관리 단위 등 상세값은 검토안이다.

프로젝트 선택 → 현황·문서 목록 → 문서 선택 → React 문서 화면. Java에서 Markdown 본문·표를 변환하고 브라우저에서 Mermaid 다이어그램을 표시한다. 추가 목업은 만들지 않는다. GitHub 로그인과 초대 제한을 적용하고 사용자가 GitHub에서 볼 수 있는 리소스만 제공한다.

## 추천 구성

| 구성 | 제안 기술 | 책임 |
|---|---|---|
| 웹 화면 | React + TypeScript | 프로젝트 목록·현황·문서 탐색 |
| 문서 화면 | commonmark-java + GFM 표 확장 + React + Mermaid | Java 본문·표 변환, React 읽기 화면, 브라우저 다이어그램 렌더링 |
| API 서버 | Spring Boot 4 + Java 25 | 로그인·세션·초대·권한 확인·대시보드 API·문서 전달 |
| 백그라운드 작업 | Spring Boot 기반 작업 처리 | GitHub 수집·재시도·문서 변환·인덱스 갱신 |
| 메타데이터 | PostgreSQL | 연결 설정·사용자·작업 큐·수집 현황·파생 인덱스 |
| 문서 산출물 | 권한으로 보호하는 저장소/revision별 캐시와 자산 저장소 | 변환 본문·다이어그램 원문·첨부 자산. 저장 배치는 상세 설계 |
| 배포 | 컨테이너 구성 | 클라우드 VM·사내 서버의 같은 실행 구성 |

사용자는 React, Spring Boot 4, Java 25를 지정한 뒤 Java 렌더러와 표·다이어그램 지원 조합의 추천을 수용했다. commonmark-java + 표 확장 + 브라우저 Mermaid를 채택하고 VitePress 제품 빌드는 대체한다. PostgreSQL·컨테이너 구성은 유지한다. ORM·정확한 의존성 버전·작업 실행 배치는 후속 상세 설계에서 정한다. 설치나 앱 구현은 아직 시작하지 않았다.

React가 프로젝트 관리와 문서 화면을 담당한다. VitePress는 비교 자료로 남고 기본 테마·검색·목차가 제품에 그대로 제공되는 것은 아니다. 문서 읽기 CSS·목차·검색은 필요한 범위에서 구현한다. Java는 API·수집·문서 변환을 담당한다. Node.js는 React 앱의 개발/배포 빌드에는 사용할 수 있으나 문서 변경마다 실행하는 Node 빌드 작업은 두지 않는다. PostgreSQL 기반 영속 작업 큐 제안은 유지한다.

## 데이터 기준

- 명세·작업 정의는 Git, 담당·실행 상태는 GitHub Issues/Projects, 구현 증거는 PR/CI가 정본이다.
- PostgreSQL은 원문을 사람이 다시 편집하는 정본이 아니다. 연결/초대/세션 등 서비스 고유 정보와 다시 수집할 수 있는 파생 데이터를 구분한다.
- 변환 문서는 연결한 저장소별로 분리한다. 저장소 이름 대신 안정된 식별자를 저장 키로 사용하고 revision·렌더러/정화 정책 버전을 함께 기록한다.
- MVP 연결 단위는 저장소 하나와 그 저장소의 문서 루트로 제안한다. 같은 GitHub Project를 공유하는 여러 저장소도 각각 연결할 수 있지만 하나의 서비스 프로젝트로 묶는 것은 후속 범위다.
- 명세 기본 조회는 dev의 최신 정상 반영본을 제안한다. main 릴리스 상태는 별도로 표시한다. 연결 대상의 실제 브랜치와 문서 경로는 설정으로 지정한다.

## GitHub 접근과 갱신

GitHub App의 OAuth 사용자 인증과 서버 설치 인증 조합을 추천한다. 사용자 토큰은 요청자의 접근 확인에, 설치 토큰은 허용된 저장소의 지속 수집에 사용한다. 설치 토큰으로 읽었다는 이유로 사용자에게 열람을 허용하지 않는다. 개인/조직 Projects의 권한·API 지원과 실제 요청할 권한은 연결 실험에서 확인해야 한다.

변경 이벤트를 받으면 저장소별 작업을 예약하고, 이벤트가 누락되거나 사내 서버에서 수신할 수 없으면 주기적으로 조회한다. 주기적 조회 간격은 초기 1분을 제안하되 저장소 수와 API 제한에 맞춰 조정한다. 이는 갱신 완료 보장이 아니다. 실제 지연에는 수집과 문서 변환 시간이 포함된다.

같은 저장소의 동기화는 직렬 처리하고 중복 이벤트는 합친다. 영속 작업 큐에 재시도 시각과 실행 임대를 기록해 프로세스 재시작 후 재개한다. 문서 변경이 없으면 문서를 다시 변환하지 않는다. Issue·Project만 변경되면 대시보드 데이터만 갱신한다.

## Java 문서 렌더링

원문 변경을 수집하면 commonmark-java로 본문과 표를 변환하고 제목·링크·다이어그램 블록 정보를 추출한다. 성공한 revision의 결과를 원자적으로 게시한다. 실패하면 이전 정상 결과와 갱신 오류를 표시한다. Mermaid 블록은 원문 코드로 분리해 React가 브라우저에서 렌더링한다.

변환 본문·다이어그램 원문·검색 결과·첨부 자산은 같은 저장소 권한 검사를 거친다. 사용자별 검색·Project 집계도 허용 범위만 반영한다. 권한 철회 후 이전 캐시로 접근을 계속 허용하지 않는다. 권한 재확인 주기와 오류 시 응답은 접근 상세 설계에서 정한다.

Markdown 변환은 HTML 정화와 별개다. 임의 script·이벤트 속성·위험 URL을 차단하고 허용한 표·앵커·접기 등만 유지한다. Mermaid는 제한된 설정으로 렌더링하고 입력 크기·복잡도 한도와 오류 표시를 둔다. 다이어그램 실패 때문에 전체 문서가 사라지지 않게 한다. 구체 라이브러리·정화 정책은 상세 설계와 검증에서 결정한다. 저장소의 코드·package.json·플러그인은 실행하지 않는다.

MVP 표현 범위는 일반 Markdown 표, 흐름도·시퀀스·ERD·클래스·상태도다. 셀 병합·복잡한 다단 표와 모든 특수 다이어그램까지 지원한다고 약속하지 않는다. Java 25에서의 파서/확장 호환성과 브라우저 렌더링은 구현 시 검증한다.

## 구현 전 확인할 사항

1. 확정된 React/TypeScript + Spring Boot 4/Java 25 + commonmark-java/표 확장 + Mermaid + PostgreSQL 구성의 세부 의존성·실행 배치를 정한다.
2. 저장소 1개를 관리 단위로 삼고 dev를 기본 문서 기준으로 사용할지.
3. 실제 GitHub App 연결 실험에서 저장소/Projects 조회와 사용자 권한 교집합을 확인할 수 있는지.

이후 API·데이터 모델·실행/검증 기준과 작업계획을 작성한다. 저장소 단위·구체적인 동기화 간격 등 제안값은 기술 스택 승인과 구분한다. 웹 편집기, SyncDoc 내부 Issue 발행 자동화, 운영 배포 자동화는 현재 MVP 읽기·집계 흐름과 분리한다.
