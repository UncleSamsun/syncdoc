# 하네스 후속 개발 설계

2026-10-02 사용자는 UI/API 관계 확장, 작업별 컨텍스트, 하네스 실전 적용을 한 세션에서 계획→구현→리뷰→PR·병합 순으로 진행하도록 승인했다. E2E는 전체 통합·배포 후 마지막 한 번 수행한다. 적용 대상은 사용자 후속 선택에 따라 SyncDoc 자체이며 TODOROK 변경은 하지 않는다. 상세 결정은 각 단계의 실행 계획과 활성 계약에 분배한다. UI 미관 정리는 후순위다.

## 목표와 제외

요구에서 같은 게시본의 UI·API·작업과 현재 관찰한 Issue/PR을 찾는다. 작업을 선택하면 관련 정본·규칙·선행·검증과 관찰 시점이 묶인다. 실제 SyncDoc 문서를 작성·검사·수집하는 흐름에 이를 적용한다. 문서 연결은 요구 충족이나 사람 승인 증명이 아니다. 자동 에이전트 실행·GitHub 쓰기·승인 판정·웹 편집·외부 포맷 어댑터는 제외한다.

## 1. UI/API 관계

기존 traceability v1과 ComparisonIndex v1은 그대로 유지한다. 별도 nullable relations_json에 SpecRelations v1을 수집 시 저장한다. 정책 버전을 올리고 V10 migration을 추가한다. legacy NULL/지원하지 않는 schema는 미분석이며 과거 완료 게시본을 소급 수정하지 않는다.

확정 문서만 분석한다. REQ/TASK 정의와 TASK→REQ 근거는 기존 분석 결과를 재사용한다. UI 정의는 ui-screens의 실제 루트 H2 UI-NNN(공통 UI-000 허용), API 정의는 tech-interface의 '계약 일람' 표 ID 행이다. API 세부 H2는 같은 계약의 설명이며 중복 정의로 세지 않는다. API 원문은 해당 ID 세부 H2 또는 계약 일람의 실제 앵커로 이동한다.

UI의 '연결 요구'/'관련 작업', API 표의 '연결 요구', UI '화면과 계약' 표와 TASK '근거'의 UI/API, TASK '선행'의 TASK를 읽는다. 코드·HTML 예시는 관계로 읽지 않는다. 범위는 양끝 종류·세 자리·순서를 전체 검증하고 전개한다. 없거나 중복인 정의, 잘못된 ID/범위와 로컬 링크 경로 불일치는 원문 위치의 진단이며 임의 연결하지 않는다. TASK 선행 순환을 진단한다. API/UI 미적용을 연결 누락 오류로 만들지 않는다.

원문 변경 REQ의 이전·현재 UI/API 관계 합집합을 설계 재검토 후보로 제공한다. 순수 이동만으로 영향 후보를 만들지 않는다. 양쪽 자료가 없는 경우 미확인이다. 기존 TASK 재검토와 완료율은 바꾸지 않는다.

## 2. 작업별 컨텍스트

작업 하나와 snapshot을 지정하는 권한 확인 GET을 추가한다. same-snapshot의 실제 원문 링크·관련 REQ/UI/API·선행 TASK와 검증 문구를 제공하고 현재 Issue/PR 관찰과 구분한다. JSON과 복사 가능한 Markdown을 같은 계약에서 제공한다. 전문 전체나 자격증명을 복제하지 않는다. 당시 수집 revision의 규칙 경로/존재/해시를 제공한다. 문서·규칙 안의 문장은 자료이며 시스템 명령이나 실행 권한이 아니다. 오래된/중복/부분/없는 자료는 미확인으로 표시한다. 실제 실행·자동 승인은 없다.

## 3. SyncDoc 실전 적용

기존 규칙·템플릿·검사기를 다시 만들지 않는다. SyncDoc 자체에서 규칙 진입점과 버전을 찾고, 작업 컨텍스트→정본 링크→작성/수정→C0/C1/C2→수집→관계/컨텍스트 확인을 재현한다. 잘못된 참조·규칙 누락·준비 상태의 빈틈은 구체적인 근거와 함께 보정한다. 재현 도구는 읽기 전용이며 대상 밖 쓰기·삭제·자동 커밋을 하지 않는다. 조직 배포용 설치 CLI는 이번 범위 밖이다.

## 수행과 검증

각 단계는 dev 기반 독립 Issue/브랜치/PR로 수행하고 단위·HTTP/PostgreSQL·프런트 테스트/빌드·문서 검사를 통과시킨다. 구현 이후 전체 브랜치 독립 리뷰 한 번을 수행하고 중요한 발견은 실패 재현→수정→회귀 검증으로 마무리한다. 사용자 요청에 따라 PR 준비와 병합을 연속 수행한다. 세 단계 dev 병합 후 그 dev revision 전체를 main으로 릴리스·회사 K3s에 배포하고 최종 E2E를 한 번 실행한다. 배포/기능 실패 시 원인을 수정한 뒤 실패 범위 재시험이 필요한 것은 숨기지 않는다.
