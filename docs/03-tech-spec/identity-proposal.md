# ID·메타데이터·참조 규칙 제안

검토 초안이다. 구현하지 않았고 세부 규약도 확정하지 않았다.

2026-09-09 참조 방식 확정: 일반 Markdown 링크의 글자에 ID를 표시한다. 참조의 활성 규칙은 [ID와 문서 참조](../../rules/identity-and-references.md)다. 아래 ID 종류와 메타데이터 필드는 계속 검토 중이다.

## 기본안

ID에는 의미를 과하게 넣지 않고 종류와 번호만 둔다. 제목·폴더·담당자·일정은 ID에 포함하지 않는다. 저장소별 이름 공간을 사용하고, 서비스 내부에서는 GitHub 저장소 식별자와 ID를 함께 사용한다. MVP의 ID 해소 범위는 한 저장소이며 다른 저장소 참조는 일반 외부 링크로 시작하는 방안을 제안한다.

| 대상 | 예시 | 역할 |
|---|---|---|
| 문서 | DOC-001 | Markdown 파일 전체 식별 |
| 요구 | REQ-001 | 독립적으로 참조할 기능/품질 요구 |
| 화면 | UI-001 | 사용자 화면 |
| 계약 | API-001 | 인터페이스 계약 |
| 데이터 | DATA-001 | 참조할 데이터 정의 |
| 작업 | TASK-001 | GitHub Issue로 연결할 구현 단위 |

번호는 최소 세 자리로 표시하되 999 이후도 허용한다. 이 예시를 모든 문단에 ID를 붙이라는 뜻으로 사용하지 않는다. 일반 설명·요약에는 항목 ID가 필요하지 않다. 추가 유형은 실제 참조 필요가 생기면 정의한다.

## 최소 문서 메타데이터

```yaml
---
id: DOC-001
kind: requirements
title: 저장소 연결 요구사항
lifecycle: draft
---
```

문서 ID, 종류, 제목, 작성 상태를 명시한다. 작성 상태의 후보는 draft/ready/retired이며 ready는 검토 가능한 문서라는 뜻이지 구현 완료나 사람의 승인을 뜻하지 않는다. 실제 허용 유형 목록은 규칙 스키마에서 한 번 정의할 예정이다.

프로젝트의 규칙 버전은 프로젝트 설정 한 곳에 둔다. 파일 수정 시각·작성자·내용 revision은 Git에서 읽는다. 진행 담당자·작업 상태는 GitHub에서 읽는다. 이 정보를 모든 문서 frontmatter에 수동 복사하지 않는다.

## 항목과 참조 표현 후보

요구에는 안정적인 ID를 두고 다른 문서에서는 일반 Markdown 링크로 연결한다. ID와 제목의 배치 및 공통 앵커 규약은 후속 정의하며, 링크 대상 앵커가 실제 존재하는지 확인한다.

본문의 연결 항목 구역에 링크를 쓰고 frontmatter에 동일한 참조 목록을 중복 작성하지 않는 방안을 제안한다. UI·API·작업은 요구 원문을 복사하지 않고 각자의 설계·검증 방법만 추가한다.

전용 ID 링크는 도입하지 않는다. 사용자는 파일 이동 빈도를 질문했고, 일반 Markdown 링크로 시작하며 이동 시 관련 링크를 함께 수정·검사하는 방식을 승인했다. 렌더러와 자동 링크 검증기는 아직 구현하지 않았다.

Issue·PR에는 GitHub에서 바로 열리는 원문 링크와 ID를 함께 남긴다. 최신 문서 링크와 작업 시작 revision에 고정한 링크는 목적이 다르므로 구분한다. 버전 고정 링크는 나중에 같은 구현 기준을 확인하는 데 쓴다.

## 발급·변경·충돌

- 새 ID는 최신 기준 브랜치의 기존 ID를 확인해 발급하고 파일 이동·제목 변경 때 유지한다.
- 동시에 다른 브랜치에서 같은 번호가 발급될 수 있다. 중복 검출을 병합 전 필수 검사로 두고, 충돌한 신규 ID와 그 브랜치의 참조를 변경한다. 목록 조회만으로 동시 발급 충돌이 해결된다고 주장하지 않는다.
- 이미 기준 브랜치에서 사용한 ID는 재사용하지 않는다. 폐기 항목의 ID와 대체 참조를 남기는 방식으로 삭제 후 재사용을 방지한다.
- 중복 ID와 없는 ID의 참조는 검증 오류로 처리한다. 초안 저장은 가능하되 정상적인 게시/구현 준비 상태로 판정하지 않는다. 폐기 항목의 참조는 대체 항목과 함께 재검토 대상으로 표시한다.
- 원문 변경이 연결된 설계·코드를 자동으로 수정하는 것은 아니다. 조회 원문은 같은 수집 revision에서 갱신하고, 파생 설계는 별도 검토한다.

## GitHub 연결

작업 ID와 Issue 번호는 분리한다. 하나의 TASK ID가 동일 저장소의 동일 Issue에 연결되도록 하고, 재등록 시 기존 연결을 확인한다. 연결 정보의 정본과 발행 재시도 처리는 GitHub 연동 상세 설계에서 확정한다. 현재 Issue·PR을 생성하거나 외부 저장소를 변경한 것은 아니다.
