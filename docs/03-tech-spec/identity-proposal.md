# ID·메타데이터·참조 규칙 제안

검토 초안이다. 이 문서의 내용 대부분은 활성 규칙으로 승격되었고, 여기에는 **아직 확정하지 않은 것만** 남긴다. [문서 작성 규칙](../../rules/spec-writing.md) §7에 따라 승격된 내용은 링크로만 둔다.

## 승격된 내용

아래는 이 문서에서 확정 규칙으로 옮겨졌다. 여기에 사본을 두지 않는다. 이 문서와 활성 규칙이 어긋나 보이면 활성 규칙이 맞다.

| 옮긴 내용 | 활성 규칙 |
|---|---|
| 문서 ID 형식·발급·유지, 삭제한 ID 재사용 금지 | [문서 작성 규칙](../../rules/spec-writing.md) §6 |
| 항목 ID 접두어 `REQ`·`UI`·`API`·`TASK`와 표기 위치 | [문서 작성 규칙](../../rules/spec-writing.md) §6 |
| frontmatter 필드 — `id`·`type`·`status` 세 개, `status` 허용 값 | [문서 작성 규칙](../../rules/spec-writing.md) §2 |
| 작성자·시각·담당자·규칙 버전을 문서에 적지 않는 이유 | [문서 작성 규칙](../../rules/spec-writing.md) §2 |
| 중복 방지 — 요구 원문을 설계·작업에 복사하지 않는다 | [문서 작성 규칙](../../rules/spec-writing.md) §7 |
| 일반 Markdown 링크로 참조하고 링크 글자에 ID를 적는다 | [ID와 문서 참조](../../rules/identity-and-references.md) |
| 전용 ID 링크 문법을 도입하지 않는다 | [ID와 문서 참조](../../rules/identity-and-references.md) |
| 파일 이동 시 들어오는 링크와 대상 `id`를 함께 확인한다 | [ID와 문서 참조](../../rules/identity-and-references.md) |
| Issue·PR에는 ID와 GitHub URL을 남기고 시작 기준을 고정한다 | [ID와 문서 참조](../../rules/identity-and-references.md) |
| 작업 ID와 Issue 번호를 분리하고 재등록 시 기존 Issue를 확인한다 | [GitHub 협업 규칙](../../rules/github-collaboration.md) §3 |
| 중복 ID와 형식 오류를 검증 오류로 처리한다 | [검증 규칙](../../rules/validation.md) C1 |

이 문서가 처음 제안했던 frontmatter 예시(`kind`·`title`·`lifecycle`, `draft`/`ready`/`retired`)는 **채택되지 않았다.** 확정된 필드는 `id`·`type`·`status`이고 `status` 값은 `초안`·`검토`·`확정`·`폐기`다.

## 아직 확정하지 않은 것

### DATA 접두어

참조할 데이터 정의에 `DATA-NNN`을 두는 방안을 제안했으나 [문서 작성 규칙](../../rules/spec-writing.md) §6의 접두어 표에 등록하지 않았다. [데이터 설계](data-model.md)가 엔티티를 표로 정의하고 있고 아직 다른 문서에서 개별 엔티티를 ID로 가리킬 필요가 생기지 않았다. 필요가 생기면 접두어 표에 먼저 등록한 뒤 쓴다.

### 저장소 사이의 참조

ID 이름 공간은 저장소별이며 MVP의 해소 범위는 한 저장소다. 다른 저장소의 항목은 일반 외부 링크로 시작하는 방안을 제안한다. 두 번째 샘플 프로젝트에 같은 규칙을 적용할 때(REQ-008) 실제로 필요한지 확인한다.

### 동시 발급 충돌 처리

서로 다른 브랜치에서 같은 번호가 동시에 발급될 수 있다. 검증기가 중복을 오류로 잡지만(C1), **충돌했을 때 어느 쪽 번호를 바꾸고 그 브랜치의 참조를 어떻게 함께 고치는지는 절차로 정하지 않았다.** 지금은 병합 전 검사에서 걸리면 사람이 판단한다.

### 폐기 항목의 참조

폐기한 항목의 ID와 대체 참조를 남기는 방식을 제안했다. 문서 단위 폐기는 `status: 폐기`와 대체 문서 링크로 정해졌지만, **항목 단위(요구·화면·작업) 폐기 표기는 정하지 않았다.** 폐기 항목을 가리키는 참조를 재검토 대상으로 표시하는 방법도 미정이다.

### 공통 앵커 규약

제목에서 생성되는 앵커는 렌더러마다 다르다. ID가 있다는 이유로 앵커가 존재한다고 가정하지 않는다는 것은 확정했지만, 공통 앵커 작성 방식은 HTML 뷰어 선정과 함께 검증한다. 검증기는 앵커 도달 여부를 검사하지 않는다.

### Issue 연결 정보의 정본

작업 ID와 Issue의 연결 정보를 어디에 두고 발행 재시도를 어떻게 처리할지는 GitHub 연동 상세 설계에서 확정한다. 현재 이 서비스는 Issue를 발행하지 않는다.

## 다음 판단

위 여섯 항목 중 `DATA` 접두어와 저장소 사이의 참조는 두 번째 샘플 프로젝트를 적용할 때, 나머지는 해당 기능을 구현할 때 판단한다. 그때 확정한 내용은 이 문서에 쓰지 않고 활성 규칙으로 올린 뒤 위 표에 한 줄을 추가한다.
