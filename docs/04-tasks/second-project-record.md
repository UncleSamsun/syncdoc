# 두 번째 샘플 프로젝트 적용 기록

[REQ-008](../01-prd/mvp-scope.md)과 [구현계획](implementation-plan.md) TASK-004의 완료 조건인 "같은 규칙을 두 개 샘플 프로젝트에 적용하고 오류 파일·항목을 정확히 제시한다"를 2026-09-10에 수행한 기록이다. 규칙의 정본은 이 저장소의 `rules/`이고, 이 문서는 적용 경과와 확인한 사실만 남긴다.

## 결정한 내용

- **대상은 `UncleSamsun/todorok`이다.** 사용자가 2026-09-10에 골랐다. 실제로 진행 중인 프로젝트이며 이 규칙 이전에 쓴 문서가 이미 있어, 빈 저장소보다 검사기의 보고가 쓸모 있는지 확인하기에 적합했다.
- **규칙만 추가하고 기존 문서는 손대지 않았다.** 사용자가 고른 범위다. todorok의 `rules/`에 이 저장소 `dev` 커밋 `db1a2e4`의 규칙 6개 파일(문서 작성 규칙, 검증 규칙, ID와 문서 참조, SDD 역할, GitHub 협업 규칙, 포맷 정의)을 그대로 복사하고, 프로젝트 값만 담은 `project-settings.md`를 새로 썼다. 적용 Spec 표는 12종 모두 사유와 함께 보류로 두었다.
- **검사기는 복사하지 않았다.** todorok은 이 저장소를 옆에 받아 `python ../syncdoc/tools/spec-validator/validate.py .`로 실행한다. 검사기 사본을 늘리면 규칙과 검사기가 따로 놀 수 있다.
- **todorok 저장소 안에서는 todorok의 CONTRIBUTING.md가 우선한다.** 이슈 연결, 커밋 형식, 기록 정책이 이 저장소의 협업 규칙과 다르다. 복사한 협업 규칙과의 차이 정리는 하지 않았고 todorok 설정 파일에 미결로 적었다.

todorok 쪽 산출물은 [이슈 #30](https://github.com/UncleSamsun/todorok/issues/30)과 [PR #31](https://github.com/UncleSamsun/todorok/pull/31)이다. 병합 여부는 그 저장소의 담당자가 판단한다.

## 확인한 사실

검사기를 todorok의 `develop` 기준 브랜치 루트에 실행한 결과다.

| 항목 | 결과 |
|---|---|
| 상태 | 오류 |
| 오류 | 8건. 문서 4개마다 frontmatter `id` 없음과 `type` 없음 각 1건 |
| 미작성 | 보류한 12종 전부 |
| C0 | 오류 없음. 복사한 규칙 표와 정의 파일이 일치한다 |
| 출력 형식 | 모두 `파일:줄 [검사] 내용`이며 절대경로 없음 |

- **오류 파일·항목·위치를 제시한다.** 4개 문서(`docs/PRD.md`, `docs/ISSUE_ROADMAP.md`, `docs/plans/` 2개)가 각각 1번째 줄에서 무엇이 빠졌는지 나온다. 이것이 이관 작업의 시작 목록이 된다.
- **보류는 오류와 구분된다.** 12종 미작성이 오류 건수에 들어가지 않고 따로 보고된다. 통과로 표시되지 않는다.
- **규칙 파일이 없는 저장소는 미검사다.** 규칙을 넣기 전 todorok 문서만 임시 폴더에 복사해 돌렸을 때 정의 파일이 없으면 미검사로 보고되는 것을 확인했다.
- **로컬 작업 폴더와 `develop`의 문서 수가 달랐다.** 사용자의 로컬 todorok에는 아직 커밋하지 않은 문서와 다른 브랜치의 문서가 있어 13개 문서에 오류 26건이 나왔다. PR은 `develop` 기준 4개 문서로 기록했다. 검사 대상은 특정 revision에 고정해야 한다는 [프로젝트 개요](../01-prd/overview.md)의 snapshot 정의와 같은 이유다.

## 드러난 한계

- **복사한 규칙 파일의 상대 링크가 깨진다.** `../docs/01-prd/mvp-scope.md`, `../tools/spec-validator/README.md` 같은 링크는 원본 저장소 기준이라 todorok에서 열리지 않는다. 검사기는 링크를 보지 않으므로 판정에는 영향이 없지만, 규칙 파일을 다른 프로젝트로 배포하는 방식은 [공통 Spec 구성안](../01-prd/spec-standard-proposal.md) §7이 미결로 둔 그대로다. 이번에는 todorok 설정 파일에 그 사실을 적는 것으로 대신했다.
- **협업 규칙은 프로젝트마다 다르다.** 문서 작성·검증·ID 규칙은 그대로 적용됐지만 GitHub 협업 규칙은 todorok의 기존 규칙과 충돌했다. 공통으로 배포할 규칙과 프로젝트가 정하는 규칙의 경계는 아직 정하지 않았다.
- **저장소 사이 참조는 필요하지 않았다.** [ID 설계 초안](../03-tech-spec/identity-proposal.md)이 두 번째 프로젝트 적용 때 확인하기로 한 항목이다. todorok에서 이 저장소를 가리킬 일은 설정 파일의 원본 표기뿐이었고 일반 URL로 충분했다. 전용 참조 문법을 도입할 근거는 나오지 않았다.

## 정본

- 규칙과 정의 파일의 정본은 이 저장소의 `rules/`다. todorok의 사본은 `db1a2e4`에 고정된 버전이다.
- 검사 항목과 판정은 [검증 규칙](../../rules/validation.md)이 정본이다.
- TASK-004의 진행 상태는 GitHub에서 읽는다. 이 문서는 완료 조건 중 두 번째 프로젝트 적용을 어떻게 했는지 남기는 기록이다.
