# GitHub 협업 규칙

상태: 2026-09-09 브랜치·리뷰·운영·릴리스 범위 사용자 확정. 구체적인 배포 절차는 미정.

## 1. 역할과 정보의 정본

- 명세에서 작업을 정의하고 GitHub Issues·Projects로 협업한다. [SDD 역할](sdd-workflow.md)과 [문서 참조](identity-and-references.md)를 따른다.
- 요구·설계·작업 범위·인수 기준은 Markdown, 담당자·논의·완료/취소 사유는 Issue, 실행 상태·우선순위·목표일은 기준 Project, 구현·리뷰·검증 증거는 PR·CI에서 관리한다.
- SyncDoc은 이 정보를 연결해 조회·집계한다. 같은 상태를 MD에서 수동 갱신하지 않는다. 연결 정보의 저장 위치와 수집 구현은 별도 설계한다.

## 2. 브랜치

- `main`은 릴리스 기준, `dev`는 개발 통합 브랜치다. 작업 브랜치는 `dev`에서 만들고 PR의 대상도 `dev`로 한다.
- 작업 브랜치 이름은 `<type>/<issue-number>-<short-description>`이다. 예: `feat/42-sync-status`, `fix/43-broken-link`, `chore/44-ci-setup`.
- type은 `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `perf`, `build`, `ci` 등 변경 목적에 맞는 종류를 사용한다. 설명은 짧은 소문자 kebab-case로 작성한다.
- 기본 단위는 작업 하나 → Issue 하나 → 작업 브랜치 하나 → PR 하나다. 여러 PR이 필요한 경우 Issue에 각 PR의 범위와 남은 완료 조건을 명시한다.
- 브랜치명만으로 작업 연결을 추론하지 않는다. Issue·PR에서 실제 링크와 작업 ID를 사용한다.
- 작업 중 `dev`가 바뀌면 필요한 변경을 통합하고 검증한다. 관련 없는 작업을 한 PR에 섞지 않는다. 작업 브랜치 → `dev` 병합은 squash를 기본으로 한다.
- 기존 저장소의 브랜치를 이 규칙만으로 생성·이름 변경하지 않는다. 프로젝트 연결 시 실제 브랜치 구성을 확인하고 적용한다.

## 3. Issue 등록

- 승인된 작업계획의 구현 작업을 등록한다. 요구 하나가 여러 작업으로 나뉠 수 있다.
- 제목에 작업 ID와 짧은 설명을 넣는다. 본문에는 목적 요약, 명세 URL과 항목 ID, 시작 기준 Spec revision, 선행 Issue를 남긴다. 인수 기준 전문을 복사하지 않는다.
- 담당자는 작업에 책임지는 사람을 assignee로 지정한다. 에이전트가 구현하더라도 책임자가 자동으로 bot으로 바뀌지 않는다.
- 등록 재시도 전 저장소·작업 ID로 기존 Issue를 확인하고 중복 생성하지 않는다. 수동 논의·배정·상태를 덮어쓰지 않는다.
- 아이디어·버그 제보는 명세 없이 Backlog에 둘 수 있지만 착수 전 작업 정의·완료 조건·필요한 명세를 마련한다.
- 작업계획 확인은 해당 계획의 Issue·Project 등록을 포함한다. 대상 저장소가 확정되지 않은 상태에서 임의의 외부 저장소에 등록하지 않는다.

## 4. Project

관리 단위마다 기준 Project 하나를 지정한다. 여러 저장소가 한 제품이면 같은 Project를 사용할 수 있다. Issue가 여러 Project에 있어도 연결 설정에 지정한 Project의 상태를 기준으로 집계한다.

보드의 작업 카드는 Issue다. 연결 PR은 구현 증거이며 별도 작업으로 중복 집계하지 않는다. 필드는 Status, 선택적인 Priority·Target date를 사용한다. 차단은 `blocked` 라벨과 사유·선행 Issue로 표시한다.

| 상태 | 의미 |
|---|---|
| Backlog | 작업 후보 또는 선행 판단 미완료 |
| Ready | 명세·작업계획·완료 조건과 선행 조건이 준비됨 |
| In Progress | 담당자가 구현·검증 중 |
| In Review | 검증 결과가 준비되어 본인 확인 또는 필요한 타인 리뷰 중 |
| Done | 인수 조건·필요 PR의 dev 병합·담당자 최종 확인 충족 |
| Canceled | 취소·중복·범위 제외를 사유와 함께 결정 |

차단은 현재 단계를 유지하며 별도 표시한다. 수정 요청을 받으면 In Progress로 돌아간다. 완료 작업을 재개하면 Ready/In Progress로 되돌리고 완료 집계에서 제외한다. Done은 개발 완료이며 릴리스/운영 배포 완료와 구분한다.

## 5. 담당 영역과 리뷰

- 개인·팀 구분 없이 본인의 업무 역할 안에서 끝나는 변경은 본인이 diff와 검증 결과를 확인하고 병합할 수 있다. 다른 사람의 승인을 일률적으로 요구하지 않는다.
- 다른 사람의 담당 영역이나 진행 중 작업과 겹치는 변경은 관련 담당자의 리뷰가 필요하다. 그 영역을 검토할 작성자 외 담당자 최소 1명의 승인을 받는다. 여러 영역이면 영향받는 각 영역의 검토가 충족되었는지 확인한다.
- 겹침은 브랜치 이름이나 Git 충돌 발생 여부만으로 판단하지 않는다. 공통 모듈·API 계약·데이터 구조 등 다른 작업에 영향을 주는 변경도 포함한다. 이는 사용자의 겹침 조건을 운영하기 위한 판정 기준이다.
- 담당 역할과 영역은 프로젝트별 설정에 기록한다. 경로 소유자는 CODEOWNERS로 표현할 수 있지만 파일 경로만으로 전체 영향이 판정된다고 가정하지 않는다. 소유 범위가 불분명하면 병합 전에 담당자를 확인한다.
- PR에는 영향 영역, 본인 영역만인지/겹침이 있는지와 근거, Issue·명세 링크, 변경 결과, 검증 결과·미실행 항목을 적는다. 중요한 수정 뒤에는 변경된 내용을 재검토한다.
- draft PR 생성만으로 리뷰 준비나 완료로 표시하지 않는다. 존재하지 않는 검사기를 통과했다고 쓰지 않는다. 문서는 링크·내용 검사, 코드는 관련 테스트 등 변경에 맞는 검증을 한다.
- 자신의 PR에 GitHub Approve를 남길 것을 요구하지 않는다. 본인 확인과 GitHub의 타인 승인 리뷰는 구분한다.
- 사람의 직접 병합 권한과 에이전트의 자율 병합 권한은 별개다. 에이전트는 PR·검증을 준비하고, 병합은 담당자의 명시적인 판단을 따른다.
- 모든 PR에 타인 승인 1회를 강제하는 설정은 이 정책과 맞지 않는다. 조건부 리뷰 강제와 실제 보호 설정은 프로젝트 도입 시 검증한다. CODEOWNERS 파일만으로 조건부 정책 전체가 자동 구현된다고 주장하지 않는다.

## 6. 명세 변경

요구·설계·작업계획은 검토 가능한 문서 PR로 준비한다. 최초 명세의 기본 통합 대상은 dev다. 승인된 작업 중 경미한 문구·링크 보정은 구현 PR에 포함할 수 있다. 요구·주요 설계·작업 범위 변경은 사람에게 확인받는다. Issue 논의에서 확정된 새 요구는 명세에도 반영한다.

일반 Markdown 링크와 안정된 ID를 사용한다. 이동 시 관련 링크를 함께 수정한다. 최신 문서 링크와 작업 시작 revision 고정 링크는 목적을 구분하고 후자를 현재 경로로 무조건 바꾸지 않는다.

## 7. 완료·취소·집계

- 코드 작업은 필요한 PR의 dev 병합과 인수 조건 충족 후 Issue를 completed로 종료하고 Project를 Done으로 변경한다. 문서·조사 작업은 명시된 산출물 검수로 완료할 수 있다.
- dev가 GitHub 기본 브랜치가 아닐 수 있으므로 `Closes #42` 자동 종료에 의존하지 않는다. PR에는 Issue URL/일반 참조를 남기고 병합 확인 후 사람 또는 승인된 에이전트 작업으로 종료한다. 전용 자동화는 아직 구현하지 않았다.
- 취소는 not planned로 종료하고 Canceled로 표시한다. Project의 모든 종료→Done 자동화가 정책을 깨지 않는지 확인한다.
- GitHub Issue와 Project 상태가 불일치하면 표시한다. Done 표기 하나만으로 검증된 완료라고 단정하지 않는다.
- 완료율은 선택한 범위의 확정 작업 중 완료 조건을 충족한 수 / 취소 제외 확정 작업 수다. 명세의 확정 작업이 Issue 미등록이라는 이유로 분모에서 사라지지 않게 한다. 후보 작업과 취소는 별도 집계한다. 분모 0은 계산 대상 없음이다. 작업 수 비율은 공수 진행률이 아니다.
- 개발 완료, 릴리스 포함, 실제 배포 성공은 별도 값이다. 릴리스에 포함되지 않은 Done 작업도 있을 수 있다.

## 8. 릴리스

담당자가 준비된 시점에 릴리스를 결정할 수 있다. 모든 작업 완료나 고정 일정까지 기다리도록 강제하지 않는다. 다른 사람의 영역과 겹치는 변경의 리뷰 기준은 릴리스에도 적용한다.

사용자는 원하는 시점의 dev 전체를 릴리스한다고 확인했다. 릴리스 대상 dev revision을 고정하고 그 시점에 포함된 전체 변경을 검증한다. 이후 dev에 추가된 커밋은 자동으로 포함하지 않는다. 일부 기능을 선택하거나 임의로 cherry-pick하는 흐름은 기본 릴리스 범위에 포함하지 않는다.

릴리스 절차의 구체화안: 선택한 dev revision에서 `release/<version>`을 만들고 포함 작업·검증 결과를 확인한 뒤 main으로 PR을 병합하고 태그/릴리스 기록을 남긴다. 준비 중 수정은 릴리스 대상 변경으로 명시하고 재검증한 뒤 dev에도 반영한다. 오래 유지하는 dev/main과 릴리스 사이 병합은 공통 이력을 보존하는 merge commit을 제안한다. 작업 PR의 squash 기본값을 여기에 자동 적용하지 않는다. release 브랜치 명명·태그 규약·실제 병합 설정은 배포 설계에서 확정한다.

릴리스 기록은 실제 포함한 revision·작업을 기준으로 하며 GitHub Release 생성 자체를 배포 성공으로 취급하지 않는다. 실제 배포 대상·명령·복구 방식은 아직 미정이다.

## 9. 적용 상태

확정된 브랜치·담당 영역 리뷰·Issue/Project 운영 기준을 문서화한 상태다. 실제 저장소, GitHub Project, 필수 검사, 담당 영역, 보호 규칙, 배포 파이프라인은 아직 설정하지 않았다. SyncDoc은 읽기·집계부터 시작하고 Issue 발행/상태 변경 자동화는 별도 구현 범위다.
