# 문서 작성 규칙

상태: 2026-09-10 사용자 확정 · 활성 규칙

[REQ-008](../docs/01-prd/mvp-scope.md)이 요구하는 공통 작성 기준의 정본이다. [공통 Spec 구성안](../docs/01-prd/spec-standard-proposal.md)의 검토 표를 이 파일로 승격했다. 두 문서가 어긋나면 이 파일을 따른다.

참조 문법과 ID 유지 원칙은 [ID와 문서 참조](identity-and-references.md)에 있고 여기서 반복하지 않는다. 검사 항목과 실행은 [검증 규칙](validation.md)을 따른다.

## 1. 적용 범위

- `docs/` 아래 모든 Markdown이 대상이다. `rules/`의 규칙 파일과 저장소 루트의 안내 파일(`README.md`, `AGENTS.md`, `CLAUDE.md`)은 대상이 아니다.
- 프로젝트는 적용할 문서 종류를 먼저 정한다. 모든 종류를 무조건 만들지 않는다.
- 프로젝트가 적용하는 문서 종류는 [프로젝트 설정](project-settings.md)의 적용 Spec 표 한 곳에서 관리한다. 적용하지 않거나 보류한 종류는 사유를 함께 적는다. 사유 없이 빠뜨리지 않는다.

## 2. 문서 메타데이터

각 문서 맨 위에 YAML frontmatter로 세 필드만 둔다. 네 번째 필드를 임의로 추가하지 않는다.

```markdown
---
id: DOC-002
type: prd-requirements
status: 확정
---
```

| 필드 | 의미 |
|---|---|
| `id` | 문서 ID. 파일명·폴더·제목이 바뀌어도 유지한다 |
| `type` | 문서 종류. 필수 내용과 검사 대상을 결정한다 |
| `status` | 문서 작성 상태. 작업 진행 상태와 다른 값이다 |

- 작성자·수정 시각·내용 revision은 적지 않는다. Git에서 읽는다.
- 담당자·작업 진행 상태·우선순위는 적지 않는다. GitHub에서 읽는다.
- 적용 규칙 버전은 적지 않는다. [프로젝트 설정](project-settings.md) 한 곳에서 읽는다.
- `status`를 본문에 다시 쓰지 않는다. 기존 문서의 `상태:` 본문 줄은 frontmatter로 옮긴다.

### status 허용 값

| 값 | 의미 |
|---|---|
| `초안` | 작성 중. 판단 근거로 쓰지 않는다 |
| `검토` | 검토 가능. 제안이며 활성 규칙·구현 기준이 아니다 |
| `확정` | 구현 기준. 어긋나는 구현은 이 문서를 먼저 고친다 |
| `폐기` | 더 이상 따르지 않는다. 대체 문서 링크를 본문 첫 줄에 남긴다 |

## 3. 문서 종류와 필수 내용

`type` 허용 값과 적용 조건이다.

| type | 문서 종류 | 적용 조건 | 필수 내용 |
|---|---|---|---|
| `prd-overview` | 프로젝트 개요 | 모든 프로젝트 | 문제, 대상 사용자, 목표와 성공 판단, 포함 범위, 제외 범위, 제약, 적용 Spec |
| `prd-requirements` | 기능·품질 요구 | 모든 프로젝트 | 요구 ID, 사용자 필요, 기대 동작과 품질 조건, 예외, 인수 기준, 근거 |
| `ui-conventions` | 공통 UI 규칙 | 사용자 화면이 있으면 | 색·글자·간격 토큰, 공통 컴포넌트, 탐색, 접근성, 공통 상태 표현 |
| `ui-screens` | 화면 명세 | 사용자 화면이 있으면 | 화면 ID, 연결 요구, 진입·종료 경로, 레이아웃, 사용자 행동, 로딩·빈 상태·오류·권한 상태, 화면 고유 검증 |
| `tech-overview` | 기술 개요 | 모든 프로젝트 | 시스템 경계, 모듈 책임·의존성, 외부 연동, 주요 흐름, 기술 선택과 이유, 검증 전략 |
| `tech-interface` | 인터페이스 계약 | API·이벤트·파일 경계가 있으면 | 계약 ID, 연결 요구, 입력, 출력, 오류, 접근 조건, 부작용, 재시도·중복 처리 |
| `tech-data` | 데이터 설계 | 영속 데이터가 있으면 | 엔티티, 필드 의미, 키·관계·제약, 수명, 변경·마이그레이션 |
| `tech-ops` | 실행·운영 | 배포·호스팅 또는 지속 실행 작업이 있으면 | 실행 환경, 설정·비밀값 주입, 배포, 상태 확인, 장애·복구, 백업 대상 또는 불필요 사유 |
| `tasks` | 작업 정의 | 구현 대상으로 정한 기능 | 작업 ID, 목적, 연결 요구·설계, 포함·제외 범위, 선행 작업, 산출물, 검증 방법, 완료 조건 |
| `proposal` | 검토 초안 | 확정 전 대안을 정리할 때 | 무엇을 제안하는지와 확정되지 않은 항목 |
| `record` | 경과 기록 | 결정 경위를 남길 때 | 결정한 내용과 근거, 어느 문서가 정본인지 |
| `guide` | 안내 | 읽는 방법·착수 방법을 알릴 때 | 대상과 먼저 읽을 문서 |

- 비기능 요구도 인수 기준을 갖는다. 임의의 성능 수치를 넣지 않고 필요한 수치와 검증 환경을 합의한다.
- 미확정 값은 질문으로 남기고, 그 값에 의존하는 작업을 구현 준비 완료로 표시하지 않는다.
- 시나리오는 요구 문서, 와이어프레임은 화면 문서, 시퀀스는 관련 기술 흐름, 설계 결정은 해당 설계에 둔다.
- 위 아홉 종류를 **명세 문서**, `proposal`·`record`·`guide`를 **명세가 아닌 문서**라고 부른다.
- 명세가 아닌 문서는 `status`가 무엇이든 **구현 기준이 아니다.** 구현 기준은 `status: 확정`인 명세 문서뿐이다. `record`의 `확정`은 기록이 완결되었다는 뜻이고 구현 기준이 되었다는 뜻이 아니다.
- 명세가 아닌 문서로 도피하지 않는다. 명세 종류에 해당하는 내용을 `proposal`·`record`·`guide`에 쓰면서 검사를 피하지 않는다.

## 4. 문서 구성

- 첫 부분에 제목과 짧은 목적, 핵심 내용, 확인할 사항을 둔다.
- 요약은 조건·예외가 있는 원문을 대체하지 않는다. 요약만 읽고 판단하게 만들지 않는다.
- 제목·표·목록으로 읽을 수 있는 Markdown을 우선한다. 도구 전용 HTML에 본문 내용을 가두지 않는다.
- 사람이 읽는 문서명은 문서의 첫 제목(`# 제목`)이다. frontmatter에 제목을 따로 두지 않는다.
- 승인 근거는 문서에 적지 않는다. 검토된 revision과 PR에서 확인한다.

## 5. 필수 내용 표기

필수 내용은 **굵은 라벨**로 적는다. 표기를 하나로 통일해 검사기가 위치를 특정할 수 있게 한다.

```markdown
**인수 기준:** 미초대 계정은 로그인 후에도 진입할 수 없다.
```

- 라벨은 `**이름:**` 형태다. 라벨 뒤에는 같은 줄에서 내용을 시작한다. 라벨만 두고 다음 줄로 넘기지 않는다.
- 표로 대체할 수 있는 필수 내용은 표 바로 앞에 라벨을 두고 표를 잇는다.

### 라벨 이름 공간

**굵은 라벨은 그 문서 종류의 필수 내용 항목에만 쓴다.** 문서 안의 세부 구획은 `###` 소제목으로 둔다. 같은 형태가 필수 항목과 임의 구획에 함께 쓰이면 읽는 사람이 명세의 골격을 구분할 수 없다.

| type | 허용하는 굵은 라벨 |
|---|---|
| `prd-requirements` | 사용자 필요, 기대 동작, 예외, 인수 기준, 근거 |
| `ui-screens` | 연결 요구, 진입, 종료, 레이아웃, 사용자 행동, 상태, 검증, 관련 작업 |
| `tasks` | 목적, 근거, 범위, 선행, 산출물, 검증, 완료 |
| `tech-interface` | 연결 요구, 입력, 출력, 오류, 접근 조건, 부작용, 재시도 |

- 위 표에 없는 이름을 굵은 라벨로 쓰지 않는다. `**지표 카드 규칙:**`처럼 그 문서에만 있는 구획은 `### 지표 카드 규칙`으로 둔다.
- 필수 내용을 반드시 라벨로 적어야 하는 것은 아니다. 산문이나 표로 적어도 된다. 다만 **라벨로 적을 때는 위 이름을 쓴다.**
- 표에 없는 `type`은 굵은 라벨을 쓰지 않는다.
- 이 규율은 명세 문서에만 적용한다. `proposal`·`record`·`guide`는 예시나 인용 때문에 다른 라벨이 필요할 수 있다.

검사기가 확인하는 라벨은 아래뿐이다. 나머지 필수 내용은 사람이 리뷰에서 확인한다. 기계가 못 보는 것을 통과로 표시하지 않기 위해 둘을 구분한다.

| type | 검사 단위 | 검사기가 요구하는 라벨 |
|---|---|---|
| `prd-requirements` | `## REQ-NNN` 섹션마다 | `인수 기준` |
| `ui-screens` | `## UI-NNN` 섹션마다 | `연결 요구`, `검증` |
| `tasks` | `## TASK-NNN` 섹션마다 | `근거`, `완료` |

나머지 `type`은 검사 라벨을 두지 않는다. 항목 단위로 반복되는 구조가 없어 라벨 검사의 실익이 없고, 내용이 표·절로 표현된다. 필수 내용은 리뷰에서 확인한다.

이 표를 고치면 [검증 규칙](validation.md)과 검사기를 함께 고친다. 문서에 없는 검사를 코드에만 넣지 않는다.

## 6. ID

### 문서 ID

- 형식은 `DOC-NNN`이다. `NNN`은 세 자리 연번이며 프로젝트 안에서 유일하다.
- frontmatter `id`에만 적는다. 본문이나 제목에 다시 적지 않는다.
- 파일 이동·이름 변경·제목 변경으로 바꾸지 않는다.
- 삭제한 ID를 다른 문서에 재사용하지 않는다.
- 이 ID로 무엇을 어떻게 참조하는지는 [ID와 문서 참조](identity-and-references.md)를 따른다.

### 항목 ID

독립적으로 참조할 항목에만 부여한다. 모든 문단에 부여하지 않는다.

| 접두어 | 대상 | 표기 위치 |
|---|---|---|
| `REQ` | 기능·품질 요구 | `## REQ-NNN 제목` |
| `UI` | 화면 | `## UI-NNN 제목` |
| `TASK` | 작업 | `## TASK-NNN 제목` |

- 새 접두어가 필요하면 이 표에 먼저 등록한 뒤 사용한다. 문서에서 즉석으로 만들지 않는다.
- 문서 ID와 항목 ID는 다른 이름 공간이다. `UI-001`은 화면 ID이며 문서 ID가 아니다.
- 항목 ID는 문서 안에서 유일하고, 같은 접두어는 프로젝트 안에서 유일하다.

## 7. 중복 방지

- 요구와 인수 기준은 요구 문서에만 둔다. 설계는 충족 방법을, 작업은 구현·검증 방법을 추가하고 상위 내용을 링크한다.
- 공통 UI 규칙과 데이터 계약은 한 곳에서 정의한다. 다른 문서에 수정 가능한 사본을 만들지 않는다.
- 같은 참조 목록을 본문과 메타데이터에 두 번 적지 않는다.
- 제안 문서의 내용을 활성 규칙으로 승격하면 제안 문서에는 링크만 남긴다.

## 8. 하지 않는 것

- 빈 템플릿 파일을 복사해 두고 내용 없이 문서를 만들지 않는다.
- 검증기가 확인하지 않는 항목을 검증 통과로 표시하지 않는다.
- `status: 검토` 문서를 구현 기준으로 인용하지 않는다.
- 문서 상태와 작업 진행 상태를 같은 값으로 쓰지 않는다.
- 조직 전체에 문서를 자동 덮어쓰는 배포를 하지 않는다. 프로젝트는 고정된 규칙 버전을 쓴다.
