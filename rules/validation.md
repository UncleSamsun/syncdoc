# 검증 규칙

상태: 2026-09-10 사용자 확정 · 활성 규칙

[문서 작성 규칙](spec-writing.md)을 기계로 검사하는 기준이다. 검사 대상 문서와 필수 내용의 정의는 그 파일에 있고 여기서 반복하지 않는다.

## 1. 검사 범위

검사기는 **세 가지만** 확인한다.

| 검사 | 확인하는 것 |
|---|---|
| **C0 정의 파일** | `rules/spec-format.json`이 정한 구조를 지키는지, 그리고 `rules/spec-writing.md`의 표와 이름이 같은지 |
| **C1 필수 문서 존재** | 프로젝트가 적용한다고 정한 문서 종류마다 그 종류의 문서가 있는지 |
| **C2 필수 항목 존재** | 각 문서에 그 종류의 필수 항목이 있는지 |

**있어야 할 것이 있는지만 본다.** 그 밖에 내용이 더 있거나, 절 순서가 다르거나, 분량이 많거나 적은 것은 검사하지 않는다.

## 2. 검사하지 않는 것

아래는 의도적으로 검사 대상이 아니다. 규칙에 있어도 사람이 리뷰에서 확인한다.

- 필수 항목 외의 추가 내용, 절 순서, 분량, 문구·표현
- 링크·앵커·이미지 경로의 도달 여부
- 항목 ID(`REQ`·`UI`·`TASK`·`API`)의 유일성과 참조 도달 여부. 문서 ID는 C1에서, `API`의 형식은 계약 일람 표에서 검사한다
- 코드 블록과 인라인 코드 안의 내용
- 외부 URL

## 3. C0 정의 파일

**입력.** `rules/spec-format.json`과, 있으면 `rules/spec-writing.md`다. 둘 다 저장소 루트 기준 고정 경로이며 프로젝트 연결의 문서 경로 설정과 무관하다.

정의 파일이 문서 종류·필수 내용·허용 라벨·기계 검사의 **기계 정본**이다. [문서 작성 규칙](spec-writing.md) §3·§5의 표는 사람이 읽는 사본이다. 검사기는 정의 파일을 읽고, SyncDoc도 같은 파일을 읽는다.

### 구조

파일은 `types` 배열 하나를 담고, 항목은 문서 종류 하나다. 일곱 필드를 모두 두고 다른 필드를 두지 않는다.

| 필드 | 의미 |
|---|---|
| `type` | frontmatter `type` 허용 값. 파일 안에서 유일하다 |
| `name` | 사람이 읽는 문서 종류 이름 |
| `spec` | 명세 문서면 `true`, 명세가 아닌 문서면 `false` |
| `condition` | 적용 조건. 사람이 읽는 문장 |
| `required` | 필수 내용 이름 목록. 사람이 리뷰에서 확인한다 |
| `labels` | 허용하는 굵은 라벨 이름 목록. 빈 배열이면 굵은 라벨을 쓰지 않는 종류다 |
| `checks` | 기계 검사 목록. 빈 배열이면 C2를 적용하지 않는다 |

`checks`의 항목은 `unit`으로 구분하는 세 종류뿐이다. `unit`마다 아래 필드만 둔다.

| `unit` | 필드 | 판정 |
|---|---|---|
| `document` | `labels` | 문서 전체에서 각 라벨이 `**라벨:**` 형태로 있고 같은 줄에 내용이 있는지 |
| `section` | `idPrefix`, `labels` | `## 접두어-NNN` 제목으로 시작하는 섹션마다 각 라벨이 있는지. 섹션이 하나도 없으면 오류 |
| `table` | `heading`, `columns`, `idPrefix` | `## 제목` 절의 첫 표에 지정 열이 있고 모든 행에서 그 칸이 채워졌으며 `ID` 열이 `접두어-NNN` 형식인지 |

정의 파일에는 버전 필드를 두지 않는다. 적용 규칙 버전은 [프로젝트 설정](project-settings.md)의 표 한 곳에서 읽는다. 문서 ID `DOC-NNN`의 형식과 항목 ID의 세 자리 연번은 정의 파일이 아니라 [문서 작성 규칙](spec-writing.md) §6의 고정 규약이다.

**판정.**

- 정의 파일이 없으면 **미검사**다. 무엇이 있어야 하는지 알 수 없으므로 통과로 표시하지 않는다.
- JSON이 아니거나, `types` 배열이 없거나, 항목에 위 일곱 필드 외의 키가 있거나 빠졌거나, `type`이 중복이거나, `unit`이 세 값이 아니거나, `unit`에 맞는 필드가 빠졌거나 남으면 **오류**다. 이때 C1·C2는 실행하지 않는다. 파일을 두고도 잘못 쓴 것이므로 미검사가 아니라 오류이며 고칠 위치가 분명하다.
- `rules/spec-writing.md`가 있으면 그 파일의 세 표와 정의 파일의 **이름 집합**을 비교한다. 다르면 **오류**다.

| 비교 | spec-writing.md의 표 (머리글로 찾는다) | 정의 파일 |
|---|---|---|
| type 집합과 필수 내용 | `type`·`문서 종류`·`적용 조건`·`필수 내용` 표. `필수 내용` 칸을 `,`로 나눈 이름 | `types[].type`, `types[].required` |
| 허용 라벨 | `type`·`허용하는 굵은 라벨` 표. 표에 없는 type은 빈 목록으로 본다 | `types[].labels` |
| 검사 이름 | `type`·`검사 단위`·`검사기가 요구하는 라벨` 표. 마지막 칸에서 백틱으로 감싼 이름을 type마다 합친다 | `types[].checks[]`의 `labels`와 `columns`의 합집합 |

- 순서, 검사 단위 열의 문장, 표 밖 산문은 보지 않는다. 검사 단위는 정의 파일의 `unit`이 정한다.
- `rules/spec-writing.md`가 없으면 이 비교를 건너뛴다. 정의 파일만 있는 저장소는 정의 파일이 정본이다.
- C0의 표 불일치는 C1·C2를 막지 않는다. 함께 보고한다.

## 4. C1 필수 문서 존재

**입력.** [프로젝트 설정](project-settings.md)의 적용 Spec 표와 `docs/` 아래 모든 Markdown의 frontmatter다.

적용 Spec 표는 아래 형식을 지킨다. 검사기가 이 표를 읽어 무엇이 있어야 하는지 판단한다.

```markdown
| type | 적용 | 사유 |
|---|---|---|
| prd-requirements | 적용 | |
| tech-ops | 보류 | 배포 설계는 TASK-008에서 작성 |
| ... | 미적용 | 해당 없음 |
```

**판정.**

| 적용 값 | 문서가 있을 때 | 문서가 없을 때 |
|---|---|---|
| `적용` | 통과 | **오류** |
| `보류` | 통과 | 미작성으로 보고. 오류 아님 |
| `미적용` | 검사하지 않음 | 검사하지 않음 |

- `보류`와 `미적용`은 사유 칸이 비어 있으면 **오류**다. 사유 없이 빠뜨리는 것을 막는다.
- frontmatter가 없거나 `type`이 허용 값이 아닌 문서는 분류할 수 없으므로 **오류**다.
- 적용 Spec 표에 없는 `type`을 쓴 문서도 **오류**다. 표를 먼저 고친다.

### 문서 식별

`type`으로 분류하기 전에 문서를 참조할 수 있는지 본다. 아래는 모두 **오류**다.

- `id`가 없다. 참조할 식별자가 없으면 파일을 옮길 때 대상 동일성을 확인할 수 없다.
- `id`가 `DOC-NNN` 형식이 아니다.
- `id`가 다른 문서와 중복된다. 중복되면 과거 참조가 조용히 다른 문서를 가리킨다.

`id`의 형식과 발급은 [문서 작성 규칙](spec-writing.md) §6, 참조 방법은 [ID와 문서 참조](identity-and-references.md)를 따른다. 항목 ID(`REQ`·`UI`·`TASK`)는 검사 단위를 찾는 데만 쓰고 형식과 유일성을 검사하지 않는다. `API`는 계약 일람 표의 열이므로 형식만 검사한다.

## 5. C2 필수 항목 존재

**입력.** 문서의 `type`과 정의 파일에서 그 type의 `checks`다.

**판정.** 검사 단위마다 요구 라벨이 `**라벨:**` 형태로 있는지 본다.

- 요구 라벨이 없으면 **오류**다.
- 라벨이 있으나 같은 줄에 내용이 없으면 **오류**다. 빈 라벨은 항목이 없는 것과 같다.
- 검사 단위가 하나도 없는 문서는 **오류**다. `prd-requirements`인데 `## REQ-NNN` 섹션이 없는 경우가 여기 해당한다.
- 검사 단위가 **문서 전체**인 `type`은 문서 안에서 요구 라벨을 찾는다. `prd-overview`가 여기 해당하며 아홉 항목이 그 문서의 완료 체크리스트다.
- 검사 단위가 **표의 행**인 `type`은 그 표를 읽어 요구 열이 채워졌는지 본다. `tech-interface`가 여기 해당한다. `## 계약 일람` 표가 없거나, 표에 `ID`·`연결 요구` 열이 없거나, 어느 행의 그 칸이 비어 있거나, `ID`가 `API-NNN` 형식이 아니면 **오류**다. 계약이 표 밖 산문에만 적혀 있으면 검사기가 볼 수 없으므로 모든 계약을 표에 둔다.
- 항목이 없을 때는 라벨을 비우지 않고 없다는 사실과 이유를 적는다. 빈 라벨은 오류이므로, 없다고 적지 않으면 빠뜨린 것과 구분되지 않는다.
- `checks`가 빈 `type`은 C2를 적용하지 않는다. `ui-conventions`·`tech-overview`·`tech-data`·`tech-ops`와 명세가 아닌 세 종류가 여기 해당한다.

## 6. 실행

검사기는 [`tools/spec-validator/`](../tools/spec-validator/README.md)에 구현되어 있다. 테스트 51개로 검사 항목별 정상·실패 fixture를 확인한다.

```bash
python tools/spec-validator/validate.py
```

- 저장소 루트에서 실행한다. 인자 없이 실행하면 현재 폴더를 루트로 보고 `rules/spec-format.json`, `rules/project-settings.md`, 있으면 `rules/spec-writing.md`, 그리고 `docs/`를 읽는다. 다른 루트나 문서 폴더는 `validate.py <ROOT> [DOCS_ROOT]`로 준다.
- 종료 코드는 오류가 있으면 1, 없으면 0이다.
- 출력은 `파일:줄 [검사ID] 내용` 형식으로 위치를 특정한다. 어느 파일의 무엇이 왜 걸렸는지 알 수 없는 출력은 실패로 본다.
- 문서를 고치지 않는다. 읽고 보고만 한다. 자동 수정을 넣지 않는다.

**실행 시점.** 문서를 고친 PR을 올리기 전, 문서 PR을 병합하기 전, 규칙 파일을 고친 뒤에 실행한다. 규칙 변경이 기존 문서를 위반 상태로 만들 수 있다.

CI 연결은 아직 하지 않는다. 실행 환경과 워크플로는 [프로젝트 설정](project-settings.md)에서 확정한 뒤 이 절을 고친다.

## 7. 보고 상태

| 상태 | 의미 |
|---|---|
| 통과 | 검사 대상이 있고 오류가 없다 |
| 오류 | 위 판정에서 오류로 정한 항목이 하나 이상이다 |
| 미작성 | `보류`로 정한 문서 종류가 아직 없다. 오류가 아니며 통과와 구분해 보고한다 |
| 미검사 | 정의 파일이 없거나, 적용 Spec 표가 없거나, 검사 대상 문서가 없다. 통과로 표시하지 않는다 |

## 8. 검증기가 지켜야 할 것

- Python 표준 라이브러리만 쓴다. 외부 의존성을 추가하지 않는다.
- 검사 항목을 늘릴 때 이 문서를 먼저 고친다. 문서에 없는 검사를 코드에만 넣지 않는다.
- 검사 항목마다 정상 fixture와 실패 fixture를 둔다. 오류가 재현되는 테스트를 먼저 만들고 통과시킨다.
- 검사기가 확인하지 않는 항목을 검증 통과로 표시하지 않는다.
- 검사 라벨을 바꿀 때는 정의 파일과 [문서 작성 규칙](spec-writing.md)의 표를 함께 고친다. 코드는 고치지 않는다. 검사 단위(`unit`)를 새로 만들 때만 이 문서와 검사기를 함께 고친다.
